结论：全书回顾

最后一课做两件事：把 20 章压成一张能背下来的图，再给你一页纸带走。作者最后一章只说了三句话，但那三句话决定了你以后怎么看待「花时间做设计」这件事。

21.1作者在最后一章说的三句话

第 21 章非常短。它不引入新概念，只回答一个问题：这本书的所有建议，代价是什么？

第一句，代价是真实的：这些做法在项目早期需要额外的工作量；而且如果你还不习惯想设计，学这些技巧的过程中你会更慢。作者没有粉饰这一点。他还补了一句更扎心的：如果对你来说唯一重要的是「让当前代码尽快跑起来」，那么思考设计就像一件苦差事，它在妨碍你达成目标。

第二句，是这本书的立场：如果好设计本身就是你在意的目标，那么这些想法会让编程变得更有趣。设计是一个迷人的谜题——如何用最简单的结构解决特定问题。探索不同的方案是有意思的，找到既简单又强大的解法是一种很棒的感觉。

第三句，是投资回报：

第 21 章 · 投资的回报

你对优质设计的投资会很快获得回报。项目开始时仔细定义的模块，会在你一遍又一遍复用它们时省下你的时间；你六个月前写下的清晰注释，会在你回来加新功能时省下你的时间。花在磨练设计技能上的时间也会回报：随着技能和经验增长，你会发现自己做设计越来越快。一旦你掌握了方法，好的设计实际上并不会比草率的设计花更多时间。

最后那句是整本书的赌注。它不是说「好设计免费」，而是说：草率设计的成本并没有消失，它只是被推迟了，并且带利息。 你在写的时候省下的十分钟，会在三个月后的某个下午以三小时的形式还回来。

作者在结尾还留了一个对「评审」场景特别有用的画面：优秀的设计师把大部分时间花在设计阶段，这很有趣；糟糕的设计师把大量时间花在复杂而脆弱的代码里找 bug。

一句能贴进评审的话：「这里省下的结构，会在三个月后以三倍的时间还回来。我们花二十分钟把它设计对，好吗？」

21.2全书主线：一张图

现在把 20 章收起来。它们不是 20 个并列的技巧，而是一条因果链：从一个敌人出发，经过它的症状与成因，走到一组具体手段，最后落在两种新出现的场景上。

① 唯一的敌人　复杂性complexity = 任何让系统难以理解和修改的东西。它不是代码量，是开发者在某一刻的体验。（L1）

② 它的三个症状　变更放大change amplification · 认知负荷cognitive load · 未知的未知unknown unknowns。前两个你能感觉到，第三个最致命——你连「这里有问题」都不知道。（L2）

③ 它的两个成因　依赖dependency · 晦涩obscurity。所有手段最终都在削这两个东西。（L2）

④ 唯一的策略　战略投资strategic investment：每次改动留 10–20% 做设计，而不是等危机过去再清理。能跑的代码是不够的。（L3）

⑤ 核心手段：深模块module　接口简单 > 实现简单。深度depth = 接口藏起的复杂度。（L4）

⑥ 怎么做到深　信息隐藏information hiding。每个模块藏一个设计决策；泄漏是最重要的危险信号red flag，尤其是时间分解temporal decomposition造成的后门泄漏back-door leakage。（L5）

⑦ 更深一层　通用模块比专用模块深；但通用代码与专用代码必须分开。（L6、L9）

⑧ 分层与合并　不同的层要有不同的抽象（否则是 pass-through）；该合的合、该拆的拆——判据是知识，不是执行顺序。（L7、L9）

⑨ 消除复杂度　把特殊情况special case定义成不存在：让错误不可能发生，而不是到处检查它。这是「降低复杂度」而非「管理复杂度」。（L8、L10）

⑩ 设计两次design it twice　动手前先想两个完全不同的方案，比较后再选。这是最便宜的一次投资。（L11）

⑪ 注释与命名　注释写代码里不明显的东西；名字要精确到能区分。写不出来，往往说明设计有问题。（L12–L15）

⑫ 修改既有代码　保持一致性consistency；让代码显而易见obvious；把「不明显」当成 bug 来修。（L16–L18）

⑬ 新场景　对任何流行做法先过复杂性这道闸门（L19）；性能问题用同一个解——简化关键路径critical path。

这条链上有一个东西是恒定的：所有的判断最后都归结为一个问题——这个决定让「理解这段代码」变容易了还是变难了？

⑦ 和 ⑧ 的位置值得留意。很多人读这本书只记住「深模块」和「信息隐藏」，然后开始到处拆类，结果越拆越乱——这正是你的第三个痛点。问题在于：深模块不是拆得细，而是藏得多。 一个 2000 行、接口两个方法的类，可能比五个各 300 行、互相调用的类更深。拆分的判据是「有几个独立的设计决策」，不是「代码有多长」。

反例 · 把「深模块」读成「多多拆类」

这样写 
// 五个类，各管一段，看起来"职责清晰"
class HeaderCodec  { Header decode(Span); };
class BodyReader   { size_t read_into(uint8_t*, size_t); };
class FrameDecoder { Frame next(); };   // 内部 new 一个 BodyReader
class Checksum     { uint32_t of(Span); };
class FrameSink    { void push(Frame); };

// 调用方每处理一帧要按顺序走四个：
FrameDecoder d(sock);
Frame f = d.next();              // 内部: HeaderCodec + BodyReader
if (Checksum{}.of(f.body) != f.sum) return kBadCrc;
sink.push(f);
为什么烂

FrameDecoder 只做一件事：把 HeaderCodec 和 BodyReader 串起来。它是第 7 章的 pass-through 层——把「一帧怎么组装」这个知识撕成了两半，而两半必须严格遵守同一个顺序约定，于是你改分片逻辑要动两个文件。

Checksum 只有一个静态方法，是典型的浅模块：接口和实现一样大。它还泄漏了一个决策——「校验覆盖哪些字节」被推给了调用方，而这是协议的一部分，本不该由调用方决定。

结果：三个决定（帧结构、校验范围、推送时机）散在五个类里，调用方还要按正确顺序调四次。 这不是深模块，这是拆得细但每个都浅。

改法：这些都共享同一个知识（线路上的帧格式），应合并成一个 FrameCodec，接口只留 next(Frame&)——它在内部完成头部解析、正文读取、校验，失败时返回错误。校验范围这个决策从此只活在一个文件里。至于 FrameSink，只有当它真的有自己的策略（背压、批处理、多路分发）时才值得独立存在。

21.3设计原则小结（21 条压缩版）

先说清两个数字：书末官方小结是 15 条，这张表是 21 条——多出的 6 条（先写注释、组合优于继承composition over inheritance、简单即快、度量、关键路径、用复杂度换收益）是从第 9、13–15、19–20 章各章正文里提炼的补充，不是书末清单的一部分。

下面是全书原则的压缩。左边是原则，右边是它针对的病症——记不住原则时，记病症，从症状反推手段更快。

全书小结 · 设计原则

复杂性是逐步增加的——你必须努力处理小事情。能跑起来的代码是不够的。持续进行少量投资以改善系统设计。模块应该较深；接口的设计应尽可能简化最常见的用法。一个模块拥有简单的接口，比拥有简单的实现更重要。通用模块更深入；通用代码与专用代码要分开。不同的层应具有不同的抽象。降低复杂度。把错误和特殊情况定义成不存在。设计两次。注释应描述代码中不明显的内容。软件的设计应易于阅读而不是易于编写。软件开发的增量应该是抽象而不是功能。

21.4危险信号小结（评审时用）

这是「说不出所以然」的解药：把感觉翻译成名字。 说不出哪里不对的时候，对照下表找最像的那一行，然后用括号里的句式说出来。

危险信号你怎么认出来
浅模块接口不比实现简单多少；一个方法只转发一行

时间分解拆分依据是「先读后写」这类执行顺序，导致两边都懂同一份格式

pass-through method签名与下一层几乎相同，实现只有一行调用

不显而易见的代码读代码的人需要额外信息才能判断它在干什么

怎么把危险信号变成评审意见

不要写「这里不太好」。写：「这是信息泄漏：单位（毫秒 vs 微秒）同时出现在 timer.h 和 stats.cc。建议把单位收进 Duration 类型，让它在两处之外无法被误读。」

格式是三段：命名问题 → 指出它出现在哪几处 → 给出一个具体改法。 三段齐了，对方就无法反驳「你说得不够具体」。

21.5留给你的三个动作

书读完了，接下来只有三件事值得做。它们都不需要重构整个项目。

① 每周一次「深模块审计」

挑一个你最近改过的模块，数两个数：公开接口有几项、实现有多少行。比值越低越浅。挑那个比值最差的，只做一件事——想办法减掉一个接口项。

不需要大改。删掉一个 getter、合并两个几乎一样的方法、把一个参数收进内部，都算。

② 评审时说出名字

下一份 MR，强制自己至少留一条带术语的意见：用「信息泄漏」「浅模块」「变更放大」「时间分解」中的任意一个。

说不出来，说明你其实没定位到问题——那就先别留意见，回去看代码。

③ 给那 10–20% 一个固定位置

抽象的投资不能靠「有空的时候」。把设计讨论塞进流程里：每次改动前，用十分钟写三行——这次改动的知识属于谁？会泄漏到几个文件？如果三个月后要改同一处，我希望只碰哪个文件？

三行写完再动手。这就是第 3 章说的战略投资，成本是一个会议的前十分钟。

21.6最后一句

这本书从头到尾只处理一件事，而它的答案异常朴素：复杂性不是靠聪明解决的，是靠一次次小选择累积出来的。

你没法一次性把系统设计对——作者在第 1 章就说了，项目开始时不可能充分预见。你只能做的是：每个增量都留一点余量给抽象，每次修改都顺手把经过的那一处弄干净一点，每次要写「以后再说」的时候真的停三十秒。

二十章的内容，最后压成一句能在你下次想抄近路时响起来的话：

能跑的代码是不够的。今天省下的结构，会在三个月后以三倍的时间还回来；而在写下的那一刻，把它设计对，几乎不花额外时间。

练习全书应用题

一个 Config 模块，get(key) 返回字符串，全项目 40 处调用各自 std::stoi、== "true"、split(',')。

「配置值怎么解析」这个决策泄漏到了 40 个调用点。改一个格式（比如支持 1k 这种后缀）就要改 40 处。修法：get_int(key, default) / get_bool / get_list，把解析收进模块——也正是第 5.4 节的例子。

一个 1800 行的 Connection 类，公开接口只有 send(Span)、recv()、state() 三个；内部管着 TLS、重连、缓冲、超时。

接口三项、实现 1800 行 —— 深。但要注意一个前提：内部是不是真的只有一个知识体？如果 TLS 和重连各自有独立的设计决策、且未来会被别处复用，那才该抽出去（第 5 章的「抽出」）。拆分的判据是决策数量，不是行数。

一个解析函数，遇到不合法输入时返回错误码，调用方有 12 处都要写 if (err) { log(); return err; }，其中 9 处其实不可能出错。

第 10 章的核心：如果这 9 处在构造上不可能失败（比如输入已在前面校验过），那正确的做法是让那个错误不可能发生——拆出一个不返回错误的窄接口，或用一个类型表达「已验证」。加断言只是把不可能情况变成崩溃，仍然占着调用方的脑子。

团队要引入一个新的「事件驱动架构」，理由是「业界都在用」。你被问意见。

第 19 章的闸门，也是第 21 章的收尾：任何新范式都要从复杂性角度被挑战。要问的具体问题是——它减少依赖还是增加依赖？它让「理解一次改动的影响」变容易还是变难？答不出来就不要上。

练习带走一页

不看上面，写下你自己版本的「三条原则」。要求：每条必须对应你真实代码库里的一个具体位置（文件或模块名），并且写出「这周我要改的那一处」。写不出来，就说明这一课还没落地。

提示：如果只能改一处，改哪一处收益最大？

没有标准答案，但有三个合格的判据：

  1. 具体到文件。「要注意信息隐藏」不合格；「src/io/reader.cc 里的 parse_header 和 writer.cc 都懂分块格式，要合并」合格。
  2. 能在一小时内动手。如果那条改动需要两周，那它不是一个动作，是一个项目——拆小。
  3. 改完能验证。怎么知道变好了？接口少了一项？某个改动从碰三个文件变成碰一个？测试变简单了？

一个真实的例子长这样：

  • 原则：同一个知识只能活在一个文件里。
  • 我的项目：net/proto.cc 和 store/serde.cc 各自实现了一遍 varint 编码。
  • 这周改：把 varint 收进 util/varint.h，两边都调它。半天。

三行写完，这本书对你就开始产生复利了。剩下的不是读，是做。

→课程到此结束

21 课走完。你现在手上有：一把量复杂性的尺子、一组可命名的危险信号、一条能贴进评审的话术，和一个关于性能的反直觉结论——让它简单，它就会快。
