实战审查：一个真实模块的三件套

前 21 课用的是玩具例子。这一课换真货：你自己仓库里那个 TCPBuf，286 行，一个藏了三个月的 double free。按深度depth、泄漏、变更放大change amplification走一遍，看这三把尺子能不能当场量出东西来。

22.1为什么挑这一段

前面的课为了讲清楚概念，例子都压到十几行。压缩是有代价的：真实代码里，一个错误的形状往往同时踩中三四课的内容，而且它不报错。玩具例子不会教你这个。

这次的材料是 Modern-Cpp-Basics/08-String & Stream/example/src/TCPBuf.h，286 行，你写的一个把 socket 包成 std::streambuf 的缓冲区。选它的理由有三条：它有真实的使用场景（stream << str 就够）；它的复杂度是自找的（一个自管内存的模板类）；它的失败方式是安静的（客户端程序跑了几十次都是好的）。

下面每一步都用真的编译器、真的 AddressSanitizer 出结果，不是推演。g++ (Ubuntu 11.4.0)，-std=c++20 -fsanitize=address,undefined。

22.2第一件：深度 —— 数两个数

第 4 课给的算法就一句话：接口有多大，实现有多少。比值越低的越深。现在对 UserManagableBuffer 数一遍。

公开接口五项：构造函数、begin()、end()、GetRawBuffer()、GetSize()、SetBuffer(T*, std::streamsize)。实现 69 行，全是 new[]/delete[] 和 std::exchange 的编排。

先别急着算比值，先查调用点。在整个仓库里 grep 这五项：

$ grep -rn "GetSize()\|UserManagableBuffer(" --include=*.h --include=*.cpp .
TCPBuf.h:35:    UserManagableBuffer(std::streamsize size)   # 定义处，零调用
TCPBuf.h:44:            bufferSize_{ std::exchange(another.bufferSize_, 0) }
                                     # GetSize() 零调用

五项接口里有两项没有调用者。 一个是 GetSize()，一个是那个按尺寸构造的构造函数。它们不是「将来可能要用」，是从写下来那天到今天一次都没被调用过。

这就是第 4 课说的「接口比必要的宽」的具体形态：它不是设计出来的，是长出来的。 写模板类的时候顺手把 GetSize() 也导出了，因为「反正别人可能想知道大小」。代价不是行数，是每一个读这个头文件的人都得为这五项分配注意力，并且判断哪几项是真的。

第 4 章 · 模块深度

模块深度是考虑成本与收益的一种方式。模块的接口越小越简单，引入的复杂性就越小。最好的模块是那些收益最大、成本最低的模块。

这句里的「成本」指的是调用方的成本，不是维护成本。所以判断一个接口项该不该留，问的不是「以后会不会用到」，而是「用到它的那一次，值不值得让所有人每次都看见它」。

一句话：接口里每一项都是永久成本，没有「暂时先留着」这一档。要么有人调它，要么删掉。

22.3第二件：泄漏 —— 谁拥有这块内存

SetBuffer 是这段代码里最有意思的一个方法。它做两件完全不同的事：

void SetBuffer(T *s, std::streamsize n)
{
    auto oldBuffer = buffer_, needDelete = !userManaged_;
    if (s == nullptr) {
        // 自己分配
        if (n == bufferSize_ && !userManaged_) return;
        buffer_ = n == 0 ? nullptr : new T[n];
        userManaged_ = false;
    } else {
        // 接管调用方给的内存
        buffer_ = s;
        userManaged_ = true;
    }
    if (needDelete) delete[] oldBuffer;
}

传 nullptr 是「你自己分配 n 个字节」；传一个指针是「接管这块内存，别 delete 它」。userManaged_ 这个 bool 存在的唯一目的就是记住走了哪条路。

现在查调用点。全仓一共四处：

TCPBuf.h:108:            inBuffer.SetBuffer(nullptr, inSize);
TCPBuf.h:113:            outBuffer.SetBuffer(nullptr, outSize);
TCPBuf.h:131:        inBuffer_.SetBuffer(nullptr, 0);
TCPBuf.h:132:        outBuffer_.SetBuffer(nullptr, 0);

四处，全都是 nullptr。 接管那条分支从来没有被走过，userManaged_ 在程序整个生命期里恒为 false。

这意味着两件事。第一，那 12 行分支代码是死的。第二，更要紧的：「这块内存归谁」这个决策被摆到了接口上，而没有任何调用方需要它。 这是第 5 课说的后门泄漏back-door leakage——不是接口太宽，是接口把内部的一个设计决定（所有权）变成了调用方必须知道的事。

第 5 章 · 后门泄漏

另一种可能的做法是从所有受影响的类中提取信息，创建一个只封装这些信息的新类。但这只有在你能找到一个从细节中抽象出来的简单接口时才有效；如果新类通过接口公开了大部分知识，那它就没提供太多价值——你只是用通过接口的泄漏替换了后门泄漏。

这段引用里的判断标准可以直接拿来用：抽出一个类之后，那个知识还留在接口上，就等于没抽。 UserManagableBuffer 确实把内存管理收进来了，但它把「谁是所有者」原样推了出去，所以它没削掉复杂性complexity，只是搬了个地方。

换个角度看会更清楚。如果明天有个调用方想复用一块已经读好的缓冲区，他得调 SetBuffer(ptr, n)，然后必须知道三件事：这个类从此不会 delete 它；生命周期得由自己管到 close() 之后；传进去的 n 必须和真实长度一致，否则 end() 会算错。三条，一条写错就是内存错误。而实际上没有人需要这个能力。

第 8 课的判据在这里特别好用：

第 8 章 · 配置参数

在导出配置参数之前，请问自己：用户（或更高级别的模块）是否能够确定一个比我们在此确定的更好的值？

同样的问题可以套到任何「参数化」上，包括这里的「让调用方决定内存所有权」。答案是不能——调用方对这块缓冲的用法一无所知，它唯一会做的就是传 nullptr。

一句话：当一个参数在全部调用点都取同一个值时，它就不是参数，是没做完的决定。

22.4第三件：变更放大 —— 那行 std::move

现在看 open()，这也是真正出事的地方。

TCPBuf *open(Socket &&socket, std::ios::openmode mode,
             std::streamsize inSize, std::streamsize outSize)
{
    UserManagableBuffer<char_type> inBuffer, outBuffer;   // :105 局部变量
    if (mode & std::ios::in)  inBuffer.SetBuffer(nullptr, inSize);
    if (mode & std::ios::out) outBuffer.SetBuffer(nullptr, outSize);

    setg(inBuffer.begin(), inBuffer.end(), inBuffer.end());
    setp(outBuffer.begin(), outBuffer.end());

    socket_ = std::move(socket);
    inBuffer = std::move(inBuffer), outBuffer_ = std::move(outBuffer);  // :121
    return this;
}

第 121 行有两个错误，套在一行里。第一个：inBuffer 是局部变量，成员叫 inBuffer_。少了下划线，于是赋值的目标和来源是同一个对象——自移动赋值。第二个：这行用逗号表达式把两个赋值串在一起，所以读的人扫过去只会注意后半截 outBuffer_ = ...（那个是对的），前半截就这么混过去了。

自移动赋值为什么致命，要看 operator=：

UserManagableBuffer &operator=(UserManagableBuffer &&another) noexcept
{
    if (!userManaged_) delete[] buffer_;              // 先释放自己的
    userManaged_ = std::exchange(another.userManaged_, false);
    buffer_     = std::exchange(another.buffer_, nullptr);
    ...
}

它没有自赋值检查。当 this == &another 时：先 delete[] buffer_ 把内存还掉；然后 buffer_ = std::exchange(another.buffer_, nullptr) —— another 就是自己，所以先读出已经被 delete 的那块指针，再赋回 buffer_。指针原地复活，指向已释放的内存。析构函数再 delete[] 一次。

AddressSanitizer 的原文：

$ ./t
ERROR: AddressSanitizer: attempting double-free on 0x506000000020
    #0 operator delete[](void*) 
    #1 Network::UserManagableBuffer<char>::~UserManagableBuffer()
    #2 Network::TCPBuf::open(Socket&&, std::_Ios_Openmode, long, long)
    #3 main  t.cpp:5
freed by thread T0 here:
    #0 operator delete[](void*)
    #1 Network::UserManagableBuffer<char>::operator=(...)

栈很清楚：operator= 释放，析构函数再释放一遍。

为什么它一直没炸

这是本课最值得记住的一段。你把 open() 的四个参数组合都试一遍（-fsanitize=address,undefined）：

modeinSizeoutSize结果
out016正常
out04正常
in160attempting double-free
in | out1616attempting double-free
in | out04正常

规律是：只要进方向真的分配了缓冲，就崩。因为只有这时 inBuffer.buffer_ 非空，delete[] 才有东西可删；inSize == 0 时 delete[] nullptr 是合法的空操作，自移动赋值白跑一遍，什么都没坏。

而你的 TCPStream.h:15 是这样写的：

void open(Socket &&socket, std::streamsize outSize)
{
    buf_.open(std::move(socket), std::ios::out, 0, outSize);
}

固定 std::ios::out、固定 inSize = 0。所以 client.cpp 跑多少次都是好的。TCPBuf 的两个方向里，进方向从来没有被真正使用过——不只是没测过，是压根没人写过。

这就是变更放大的反面教材：这个 bug 不是写错的，是被一个没有调用者的方向保住的。 三个月后有人想做「双向 TCP 流」，往 open() 里传 std::ios::in，程序会在第一天就 double free，而他会认为是自己的调用方式不对。

编译器本来能帮你

clang++ 对 b = std::move(b); 直接报 -Wself-move：

mech.cpp:14:34: warning: explicitly moving variable of type 'B'
to itself [-Wself-move]
   14 | int main(){ B b(new char[16]); b = std::move(b); }
      |                                ~ ^           ~

但 g++ 11 不认这个开关（unrecognized command-line option '-Wself-move'），默认也不报。你一直用 g++，所以这行代码在你眼前是安静的。真要防这一类，把 clang 的 -Wall 加进 CI，比靠人眼可靠。

22.5反例：只修那一行

反例 · 「一行就修好了」

这样写 
// 把 :121 的 inBuffer 改成 inBuffer_
inBuffer_ = std::move(inBuffer),
outBuffer_ = std::move(outBuffer);

// 或者更"稳"一点：给 operator= 加自赋值保护
if (this == &another) return *this;
为什么烂

两种改法都能让 ASan 闭嘴，但它们只修了症状。根因是那个类本身：一个既分配又接管、靠自己记 userManaged_ 的模板类，为一条零调用者的路径付了全套代价——手写移动构造、手写移动赋值、手写析构、一个 bool、一个 GetSize()。

加 if (this == &another) 是在给这份多余的成本再交一笔保险费：这段代码以后每个读者都要问「什么情况下会自赋值」。而更该做的是先问「这个类需要存在吗」。

改法不是加检查，是把整个类删掉，换成 std::vector。所有权、移动、析构、大小，四件事标准库全包了；userManaged_ 那条从没走过的路径跟着一起消失。原码 286 行，换完 210 行，UserManagableBuffer 和 userManaged 在文件里各出现 0 次。

TCPBuf *open(Socket &&socket, std::ios::openmode mode,
             std::streamsize inSize, std::streamsize outSize)
{
    close();
    if (mode & std::ios::in)  inBuffer_.resize(inSize);
    if (mode & std::ios::out) outBuffer_.resize(outSize);

    char_type *ib = inBuffer_.data();
    setg(ib, ib + inBuffer_.size(), ib + inBuffer_.size());
    char_type *ob = outBuffer_.data();
    setp(ob, ob + outBuffer_.size());

    socket_ = std::move(socket);
    return this;
}

改完的 open() 不再有局部缓冲、不再有移动赋值、不再有可能写错的成员名，因为没有那个可以写错的地方了。close() 里原来两行 SetBuffer(nullptr, 0) 变成 inBuffer_.clear(); outBuffer_.clear();，TCPBuf.h:178 的 outBuffer_.GetRawBuffer() == nullptr 变成 outBuffer_.empty()。

实测：真 socket 回环，open / sputn("ping1", 5) / close 走通，server 收到 5 字节，ASan 和 UBSan 全程无输出；连续两次 open() 重开也不炸。

22.6但还有第二个洞

换完 vector 之后，只跑输出方向是好的。可是把 mode 加上 std::ios::in 再测，sgetn 返回 0，一个字节都没读到，而且不报错。

原因不在缓冲，在别处：TCPBuf 根本没有重写 underflow() 和 xsgetn()。grep 一遍就知道：

$ grep -c "underflow\|xsgetn" TCPBuf.h
0
$ grep -c "underflow\|xsgetn" example-answer/src/TCPBuf.h
3

basic_streambuf 的默认实现是：输入缓冲用完了就返回 eof。open() 里你 setg(ib, ib + n, ib + n)——三个指针都指向末尾，读位置等于读终点，所以第一次读就是「已到尾部」。没有 underflow() 去 recv() 补数据，进方向永远是空的。

这是第 7 课说的一类问题：接口看起来完整，语义却是半截的。TCPBuf 暴露了 std::basic_streambuf 的全部能力（读写都继承来了），但只实现了写那一半。调用方没法从类型上看出这一点，只能踩一次。

第 16 章 · 每一个改动都引入复杂性

每一个最小的变化都会引入一些特殊情况、依赖性或其他形式的复杂性。如果你没有使设计变得更好，则可能会使它变得更糟。

作者这句话在这里有个很实际的用法：修 bug 的时候，用「改完之后设计有没有变好」当验收标准。 只把 inBuffer 加个下划线，设计变差了一点点（多一个读者要理解的自赋值路径）；删掉整个类换 vector，设计明显变好了。同样是「修好了」，一个值得合，一个只是把地雷埋深。

一句能贴进评审的话：「这个类的三条路径里有一条从没被调用过（SetBuffer 传非空指针），却要为它维护手写的移动语义和一个 userManaged_。我建议删掉它，改用 std::vector，286 行能降到 210 行，那个自移动的坑也跟着消失。要不要我先开一个 PR？」

练习你来判

一个 Buffer 类同时支持「自己 new」和「接管传入的指针」，用 bool owned_ 区分。全项目 4 处调用，全部 SetBuffer(nullptr, n)。

「这块内存归谁」这个内部决策被推上了接口，属于信息泄漏；而四条调用点全都走同一条路，说明有两种模式的那个参数是过度暴露。两者叠加的结果就是那个 bool 恒为 false，接管分支成了死代码。修法不是加断言，是删掉一条路径。

open() 崩溃只在 mode & std::ios::in 且 inSize > 0 时出现；自带的 client.cpp 固定传 out, 0, n，从来没炸过。

三条都沾边，但最准确的命名是第三个：缺陷被一条零调用者的代码路径藏住了。 加测试能发现它，但那是在为一条没人需要的路径写测试；更该做的动作是先决定这条路径该不该存在。

修完 double free，sgetn 仍然返回 0，因为 TCPBuf 没重写 underflow()。你要写进评审的是哪一句？

重点不是「有个 bug 要补」，而是「类型的接口比它的实现宽」：读写都从 basic_streambuf 继承了，但只兑现了写。可选的修法是收窄接口（只暴露输出流），而不是把输入那半也补齐——除非真的有人需要双向。

练习换到你的代码上

下面四种「下一步」，哪一种最符合这三件套给出的顺序？

打开你现在手上正维护的一个模块，数三个数：公开接口有几项、其中几项没有调用者、有没有一条分支从没被走过。三个数写下来，一个都不许估。

提示：grep 一遍方法名，比读代码快十倍。

没有标准答案，但有三个判据能判断你数对了没有：

  1. 零调用项必须是 grep 出来的，不是想出来的。 包括 this 内部的隐式调用、宏里的调用、只在注释里出现。用 grep -rn "GetSize(" --include=*.h --include=*.cpp .，看到定义处之外没有命中才算数。
  2. 死分支要能说出「哪条路径没人走」。 「if (mode == kSpecial) 里 kSpecial 没有任何调用方传入」合格；「有些分支可能没测」不合格。
  3. 数完之后必须有一个可以当场做的动作。 删掉那两项零调用接口，或者把那条死分支对应的参数从签名里去掉。如果三个数都数完了却动不了手，说明它们都被人依赖着——那也是个结论，但和你以为的不一样。

这段代码的三行答案长这样，可以照抄格式：

  • 模块：example/src/TCPBuf.h（286 行）
  • 接口 5 项，零调用 2 项：GetSize()、UserManagableBuffer(std::streamsize)
  • 死分支：SetBuffer 的接管路径（s != nullptr），全仓 4 处调用都是 nullptr

→这一课真正留下的东西

三件套走完，你会发现抓住 bug 的不是「读代码读得仔细」。是三个可以数的问题：接口几项、其中几项没人调、哪条分支没人走。 数完，那个 double free 就自己浮出来了，因为它在一条没人走的路上。
