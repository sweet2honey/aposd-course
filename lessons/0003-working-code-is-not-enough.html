工作代码是不够的

前两章讲清了复杂性complexity是什么。这一章讲为什么明知如此，我们还是在制造它，以及那个唯一可行的解药：把设计当成投资，每次都投一点。

3.1两种编程风格

战术编程tactical programming

目标是让功能跑起来。每个任务上做一点小妥协，因为「就这一次，问题不大」。

单个决定都合理，累积起来是灾难

战略编程strategic programming

目标是好设计 + 能工作。作者的要求很硬：几乎每一个任务都要这样，而不是重大重构时才想起来。

把设计当成持续投资，而非开销

战术编程的杀伤力不在于某次妥协有多糟，而在于那句「就这一次」在每一个任务上都成立。于是：小的妥协 → 系统变脏 → 下一个改动更难 → 更想走捷径 → 更脏。作者把这个循环描述得很具体：几个星期或几个月后，问题开始显现，而这时清理已经需要几个月的工作量。而你又告诉自己「先让下一个功能跑起来比回头重构更重要」，于是继续打补丁。

第 3 章 · 战术编程为什么是短视的

如果你用战术方式编程，你会尽量快地把任务做完。也许你有一个很紧的期限，于是为将来做计划不是优先事项，你不会花太多时间寻找最好的设计，只想尽快让某个东西生效。你告诉自己：为了把当前任务做得更快，增加一点复杂性、或者引入一两个小问题，没什么大不了。这就是系统变复杂的方式——不是某个特定事物造成了复杂性，而是数十或数百个小事积累的结果。

战术龙卷风 tactical tornado

战术编程者的极端形态：产出惊人、上线飞快，身后留一地废墟。管理层把他当英雄，因为废墟的账单由后来的人付。作者补了一句很刻薄的话：英雄是那些接手废墟、把它重新整理好的人。

落到 C/C++ 的日常里，战术编程的痕迹长这样：一个新的 #define MAX_XXX、一份复制粘贴的解析循环、一个「暂时先不做边界检查」的 memcpy、一个为了赶 demo 加上去的 static 全局标志。每一条单独看都能自圆其说。但它们都会在两年后变成某个人的深夜事故单。

第 3 章 · 主动与被动投资

有些投资是主动的。比如为每个新类花一点时间去找一个简单的设计：不要直接实现你想到的第一个方案，而是试几种替代设计，挑出最简洁的那个；设想将来系统可能以哪几种方式被改动，并确保设计能应付这些改动。写好文档也是主动投资的例子。另一些投资是被动的：无论你事先投入多少，设计决策里都不可避免地会出错，随着时间推移这些错误会变得明显。发现设计问题时，不要忽略它，也不要补丁了事，多花一点时间去修好它。

比例：总开发时间的 10–20%。作者把这个数字说得很死，也给了它的账：

初期你会慢 10–20%；但几个月内，收益就会超过成本，之后你持续比战术路线更快。反过来，如果从不投资：第一个项目上你快 10–20%，但从此以后每一个项目都慢 ≥10–20%，而且这个惩罚贯穿整个生命周期。

这里有个不对称：省下的时间是一次性的，付出的代价是永久的。书里把这两条路线画成一条生产率随时间的曲线：

「主动投资」在底层代码里是什么样子

不是「加个抽象层」，往往相反。举三个具体的：

  • 先想清楚所有权，再写第一行。这块内存归谁？谁 free？出错路径上谁来收？花二十分钟把这个定下来，比事后追一个每周泄漏 4KB 的 bug 便宜太多。
  • 先想清楚错误怎么表达。返回 int + errno？Result<T, E>？还是 out 参数？三种都行，但不能混。混着用的模块module，调用方每写一行都要重新判断。
  • 试第二种接口。第一个想到的接口永远是「实现的镜像」。把实现放一边，先写调用方最想看到的三行代码，再倒推接口。这个动作十分钟，经常能省掉一整层。

3.3「等成功了再清理」为什么不成立

创业公司的经典论证：早期生存压力大，先跑起来，成功之后雇人清理。作者逐条反驳：

  1. 一旦变成意大利面，几乎不可能修。不是「花钱就能修」，是「修不动」：清理需要先理解系统，而系统已经不可理解。
  2. 好设计和坏设计的回报都很快。「以后再优化」这个前提是假的：战略投资strategic investment的收益在几个月内就出现，并不需要等到遥远的未来。
  3. 坏代码库招不到、也留不住好工程师。这是最实际的一条。人不是机器，烂代码本身就是离职原因。

书里给的对照很有说服力：Facebook 早期口号是「Move fast and break things」，后来改成了「Move fast with stable infrastructure」，连它自己都发现前半句的下半场代价太高。Google 和 VMware 从一开始就是战略路线，也没因此死掉。

第二条要再强调一次，因为它推翻了很多人心里的错误前提：他们以为「好设计」是一笔要等到遥远未来才回本的投资，所以短期当然该省。作者说不是：几个月的量级就开始回本。你不需要活到三年后才有资格享受好设计：下一个人改这段代码时，账单就开始还了。

最危险的一句话

「先战术一下，回头再补。」作者说这是滑坡效应，不是风险提示：一旦开始往后拖，几乎必然再拖一次，因为每拖一天问题就更大一点、方案就更可怕一点。拖延不会自愈，只会自我强化。

第 3 章 · 滑坡效应

一致地采用战略方式、并且把投资当成当下就该做的事而不是将来要做的事，这一点至关重要。当你陷入危机时，很容易把清理推迟到危机结束之后，但这是一条滑坡：推迟一次之后，几乎肯定会再推迟一次。一旦开始推迟设计改进，就很容易让推迟变成永久的，并把整个文化拖进战术编程里。你等得越久，问题就越大，解决方案就越令人生畏，于是推迟起来也就越轻松。

这条在本章末尾会收成一句非常反直觉的结论：最有效的做法不是找到一次大重构的机会，而是让每位工程师持续做小额投资。设计不是项目的阶段，是每次改动里的十五分钟。

3.4为什么这个取舍在评审里特别难

这一章的难处不在「知道」，而在「当场判断」。评审的时候，你看到一个 60 行的函数里塞了两件事，直觉告诉你不该合着；但另一边赶着上线，你又说不出它到底会造成什么后果。于是你放过它。

作者给的处理方式可以总结成两条简单规则，专门治这种说不出口的场合：

情况怎么办判断依据
修复成本 < 半小时，且明显减少依赖dependency当场做，别记录被动投资的最小单位
修复会牵动大范围 / 有风险记录并明确说这是债务区别在于「有意识的决策」与「习惯性绕过」

第二条的重点在别处：作者并不要求你在任何情况下都停下来重构。他要的是不假装没看见。写下「这里有两份解析逻辑，格式一改要改两处，暂时不合」这句话的成本是三十秒，而它的价值是让这个决策从此可见，下一个人不会在毫不知情的情况下踩上去。这就是「有意识的绕过」和「习惯性绕过」的全部区别。

这也直接回应了第三个痛点的前置条件：模块拆得对不对，取决于你有没有把「该拆的理由」和「暂时不拆的理由」都写下来。凭感觉拆，越拆越乱；按知识边界拆（第 5 章），才有稳定的判据。

反例

这样写 
/* 战术路线：急着上线，先这样 */
static int handle_msg(int fd, const uint8_t *buf, size_t n) {
    struct header h;
    memcpy(&h, buf, sizeof h);          /* 假设 buf 够长 */
    if (h.magic != 0xCAFE) return -1;

    /* 业务逻辑直接写在这，顺手算个校验和 */
    uint32_t sum = 0;
    for (size_t i = 0; i < n; i++) sum += buf[i];
    if (sum != h.checksum) return -1;

    return dispatch(fd, h.type, buf + sizeof h, n - sizeof h);
}
为什么烂

三个战术妥协叠在一个函数里：memcpy 没检查 n >= sizeof h（越界读，攻击面）；校验和算法硬编码在这里，而协议这个字段的定义在另一个文件里另有一份（信息泄漏information leakage，第 5 章）；dispatch 拿到的是裸指针 + 长度，任何调用者都可以随便构造一个不满足不变式的参数。

单看每一处都「先这样能跑」。但下一个要加消息类型的人会先发现校验和算错了，然后发现没法单独测试 handle_msg，因为它把解析、校验、分发三件事焊死了。

改法：把「报文的内部布局与校验」收进一个模块，接口给 msg_parse(buf, n, &msg) -> Result<msg_view, parse_err>，越界和校验都在里面处理，调用方拿到的是已经验证过的视图。handle_msg 退化成十行：解析、查表分发、返回。投资额大概四十分钟，回本点是下一个人加消息类型的时候，他只需要改一张表。

练习你是哪种工程师？

场景 1你接到一个数据导出需求。第一种实现写成 80 行、塞在 handler 里、能跑。你意识到还可以抽成一个独立的导出模块，多花 40 分钟。按本书，你该怎么做？

场景 2你在读一段旧代码，发现两个模块各自实现了一遍同一种配置文件的解析。此刻你的任务是改一个无关的 bug。按本书，你的最佳选择是？

场景 3团队赶一个发布会，CTO 说：「这两个月先快速堆，之后我们会有专门的重构季度。」最符合本书的回应是？

可以贴进 code review 的原话：「这次改动只花五分钟就能把这条知识收进一个模块，为什么不留到下次？按 10–20% 的投资比例，这属于当场就该做的那一半。」
