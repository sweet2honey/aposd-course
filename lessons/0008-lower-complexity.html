降低复杂性

一个不可避免的复杂度摆在你面前：你可以自己扛，也可以推给调用方。这一章只讲一件事：该谁扛，以及为什么几乎总是你扛。

8.1把麻烦往下压

设想你在写一个新模块module，碰到一个绕不过去的复杂度。它不会消失，只能落在某处。两个选项：

  • 往下压：模块自己在内部消化它，调用方完全不知道它的存在。
  • 往上推：模块把决定权交出去：抛异常、要参数、要回调、要调用方先做一步预处理。

书里的答案有个很朴素的算术：

第 8 章 · 谁该扛这个复杂度

如果这个复杂度与该模块提供的功能有关，那么第二个答案通常是错的：大多数模块的使用者比开发者多，所以麻烦开发者，比麻烦使用者要好。

作为模块的开发者，你应当努力让使用者的日子尽可能轻松，即使这意味着你自己要多干一点活。换一种说法：模块拥有简单的接口，比拥有简单的实现更重要。

这个算术在底层代码里尤其成立，值得展开。一个 read() 的包装如果多要求调用方检查一个返回码，而它有一千个调用点，那么这个「省事」实际是把一个决定复制了一千份。而如果包装自己在内部处理掉，成本是一份。

书里也点破了人为什么会反过来做：把简单的问题先解决、把难的问题推给别人，短期内自己的日子最舒服。抛个异常、加个配置项，今天就能收工。代价是隐形的、分散的，落在未来和别人的身上。

8.2配置参数configuration parameter：把决定权当礼物送出去

这是本章最锋利的一节，也是底层项目里最常见的「伪设计」。

典型过程是这样的：你在写一个页缓存，不确定缓存多大合适。于是：

struct CacheConfig {
    size_t capacity_pages;      // 缓存多少页？
    size_t prefetch_ahead;      // 预读几页？
    int    eviction;            // 0=LRU 1=CLOCK 2=ARC？
    size_t flush_batch;         // 一次回写几页？
};

class PageCache {
public:
    explicit PageCache(const CacheConfig& cfg);
};

看起来非常专业：灵活、可调、适应不同负载。实际发生的事是：

  1. 你把「多大合适」这个你本该想清楚的问题，换成了「请告诉我要多大」。
  2. 每个部署、每个测试、每个下游库，都得自己填四个数字。填错了没人报错，只是慢或 OOM。
  3. 这些值会过时。你换了淘汰算法、换了设备，配置文件里那四个数字还在，而且没人敢改，因为不知道当初为什么这么填。
第 8 章 · 配置参数

配置参数还提供了一个轻松的借口，让人可以不去处理重要问题，而是把它转嫁给别人。在很多情况下，用户或管理员很难、甚至无法确定参数的正确值；而在另一些情况下，只要系统实现多做一点工作，就能自动算出正确的值。

所以应当尽可能避免配置参数。在导出一个配置参数之前，先问自己：用户（或更高层的模块）能比我们在这里确定得更好吗？ 理想情况下，每个模块都应当完整地解决问题；配置参数导致解决方案不完整，从而增加系统复杂性。

「自动算」长什么样

书里的例子是网络重传间隔：与其导出一个 retry_interval_ms 让人去猜，不如让协议测量成功请求的响应时间，取其若干倍作为重试间隔。好处有两个：用户不用懂；条件变化时它会自动适应。

页缓存同理。下面这个接口没有一个可调旋钮，但它在真实机器上通常比那四个数字更准：

class PageCache {
public:
    // capacity 不给：取 min(可用内存的 1/8, 设备容量)。
    // 预读：按顺序访问的命中率自适应调整。
    // 淘汰：LRU 起步，检测到扫描型负载时切到 CLOCK。
    PageCache();
};

但这并不意味着「不要可配置」。书里留了口子：当用户确实比实现更懂时才该导出参数（比如优先级——用户知道哪个请求更急），并且应该给一个合理的默认值，让参数只在特殊情况special case下才需要被填。

判断一个参数该不该存在，问三句：
① 用户能比我们算得更好吗？
② 如果填错，系统会报错吗，还是只是悄悄变慢？
③ 我们能不能给一个「大多数情况都对」的默认值，让这个参数默认不用出现？

8.3同一个原则的两个正例

「往下压」不只是「别抛异常、别加参数」，它有一个更积极的形态：把调用方本来要做的几步，变成模块内的一步。

文本编辑器的经典对照

行导向接口：UI 要做「在行中间插一个字符」，得拆行、插入、合并、修后面所有行号。

字符导向接口：insert(pos, text) 一次搞定。实现变复杂了（内部要拆并行），但这段复杂性complexity被封装在模块内部，只写一次，而不是在 UI 的十几个地方各写一遍。

原子写文件

「写临时文件 → fsync → rename → fsync 目录」这四步，如果交给每个调用方做，一定会有人漏掉第二个 fsync。

把它压进 atomic_write(path, bytes)：调用方一句，正确性只由一处保证。文件的实现更难写了，接口却更好用了。

这两个例子的形状完全一样：复杂度没减少，只是从 N 个调用点搬到了 1 个实现里。 这就是「降低复杂性pull complexity downward」在这个语境下的准确含义：不是让问题消失，是让知道它的人数从 N 降到 1。

8.4但别压过头

书里专门有一节讲这个，因为「降复杂度」太容易变成万能借口。判断标准有两条，必须同时满足：

  1. 被压下去的复杂度，与这个类已有的功能密切相关；
  2. 压下去之后，系统其他地方会有一批简化。

反例就在第 6 章：给文本类加一个 backspace() 方法。表面上看这是「降低复杂性」：UI 不用自己算删哪个字符了。但它违反了第一条：退格是 UI 语义，跟「管理文本」的核心功能无关。结果不是降低复杂度，而是信息泄漏information leakage：文本类从此知道 UI 的存在。

书里对这个反例的判词很准：把 UI 知识加进文本类，并没有显著简化上层代码，反而把两个模块绑在了一起。

反例

这样写 
// 「帮调用方把麻烦都处理掉」——处理过头了
class Conn {
public:
    // 内部重试 3 次、超时 5s、失败返回空 buffer
    std::vector<std::byte> request(const Request& r);

    // 内部解析协议、校验 checksum、反序列化
    std::optional<Response> request_parsed(const Request& r);

    // 内部重试 + 解析 + 业务层缓存
    std::optional<Response> request_cached(const Request& r);
private:
    /* … */
};
为什么烂

① 三个方法做的是同一件事的三层包装，调用方不知道该用哪个（认知负荷cognitive load）；② 「重试几次」「超时多久」被硬编码进 Conn，需要不同策略的调用方无路可走，只能绕开这个类自己写 socket 代码；③ request_cached 把业务缓存塞进传输层：缓存失效策略属于业务，不属于连接；④ 每一个 request_* 变体都要求 Conn 懂更多别处的知识，信息泄漏四处开花。

这不是「往下压复杂度」，而是把三个不同层的职责压进了同一个类。压下去的必须是「与本模块功能密切相关」的复杂度；重试策略、协议解析、业务缓存，没有一个属于「一条 TCP 连接」。

改法：按层拆回去，每层只压自己那份。Conn 只管「发字节、收字节、报告错误」；重试策略放 RetryPolicy（或调用方）；协议解析放 Codec；业务缓存放业务层。然后在每一层内部把该层的麻烦吃干净：Conn 自己处理 EINTR、自己处理短写、自己在关闭时报告清晰的错误，这些才是它该扛的。

一个实用的自检：如果把这个类名换掉，它内部做的事还讲得通吗？ Conn 里做业务缓存，换成任何名字都别扭，这就是信号。

8.5为什么这对「评审说不出所以然」有用

痛点二是「评审时只会说『不太好』」。这一章给了你一句有推论支撑的话，而不是一个感受：

当你看到 void f(int flags) 或者 Config{...} 被传进一个模块，你可以问：这个值，模块自己能不能算出来？

  • 能算 → 参数不该存在，模块没把问题解决完。
  • 不能算，且用户更懂（优先级、业务意图）→ 参数合理，但要有默认值。
  • 不能算，用户也不懂（缓存大小、重试间隔）→ 这是把难题推给了不懂的人，最糟的一类。

这三句话比「这个设计不太好」有力得多，因为它指向了具体动作：删掉这个参数，或给它算一个默认值。

8.6一条给底层代码的补充

书是通用软件设计书，但这一章在系统编程里有额外的分量，值得说清楚，因为「往下压」在那里不是风格问题，是正确性问题。

错误处理的归属，决定了系统在故障下的行为。「每个调用方自己检查返回值」这种设计，在有一千个调用点的代码库里等价于「总有一个地方忘了检查」。把它压进一层（内部重试、内部转成 Result、或按第 10 章的办法让错误不存在），正确性就从「N 处都要对」变成「1 处要对」。

但这要求压下去的那一层真的懂。如果 Conn 不懂业务，它就没法决定「这个错误该重试还是该上报」，这时正确的做法不是硬压，而是把决定权和执行权分开：Conn 负责准确报告（Result<T, Err>，错误类型分明），策略留给懂的人。这仍然是「降低复杂性」，只是压的是「机械的麻烦」（EINTR、短写、超时计算），而不是「语义的判断」。

一句话的判据：机械性的麻烦往下压，语义性的判断往上交。 前者压得越干净越好，后者压下去就会变成猜。

练习哪个参数该删

单选下面四个配置项，哪一个最应当删掉、由模块自己算？

练习压下去，还是推上去

模块在写文件时可能遇到 EINTR，现在把这个 errno 原样返回，要求调用方重试。

EINTR 是纯粹的机械麻烦，与语义无关，模块内部循环重试即可。返回它只是把「正确性」复制到了每个调用点。

一个 RPC 客户端在连接失败时，不知道业务上该重试还是该向用户报错，于是自己重试 3 次后放弃。

这是语义判断，模块不懂业务就没资格决定。正确做法是返回分明的错误类型，让懂的人决定。注意这跟「做成配置」不同：配置是把决定推给不懂的人。

调用方每次用 PageCache 前都要自己算出「该读哪几个页、按什么顺序读」。

页的选取与顺序是「页缓存」这个抽象的核心职责；让调用方算，等于把模块的核心工作外包了出去。

一个序列化库要求调用方先 reserve(n) 再逐条 push，n 算错就会静默截断。

「容量够不够」是库自己知道的事（它知道每条多大），却让调用方去算，而且算错不报错。这是把内部知识外泄 + 制造未知的未知。库应自己扩容。

练习重写一个「灵活」的接口

你的 BufWriter 有四个参数：capacity、flush_threshold、sync_on_drop、max_batch。团队里没人说得清后三个该填什么，测试里各填了不同的值。用第 8 章的办法重写它，并说明每个参数的去向。

提示：逐个问「模块能不能自己算」。

先分类，再动手：

class BufWriter {
public:
    // capacity 有默认值，且默认值来自实测：64 KiB 在多数设备上
    // 已能吃满顺序写带宽，再大只增延迟。
    explicit BufWriter(size_t capacity = kDefaultCapacity);
    ~BufWriter();                       // 析构时必然 flush，不询问

    void write(std::span<const std::byte>);
    void flush();                       // 显式刷盘，语义单一
};

四个参数的去向：

  • capacity → 保留，但给默认值。它是部署/负载相关的事实，调用方可能真知道；默认值让 90% 的调用点不用写它。
  • flush_threshold → 删掉。它和 capacity 是同一件事的两种说法（写满就刷），两个旋钮只会互相打架。
  • sync_on_drop → 删掉。析构函数不该有两种语义。这是「用户能比我们决定得更好吗」的典型反例：两种选择都会有人踩坑，而其中一个（丢弃数据）是错的。要么永远 flush，要么根本不缓冲。
  • max_batch → 删掉，内部算。批量大小取决于底层 write() 的行为，模块比调用方更清楚，应该自己探测。

收益是具体的：调用点从「四个数字」变成「零个或一个」；测试不用再为每个组合造用例；sync_on_drop 那个「有时丢数据」的 bug 类别直接消失。

边界在哪：如果确实有调用方需要「绝不阻塞的 flush」（比如信号处理路径），那应该新增一个不同的方法（try_flush()），而不是给同一个方法加一个布尔开关。开关会让两条路径共享一份实现，而它们的行为要求恰好相反。

→带走什么

这一章可以压缩成一个动作：把模块的公开接口摊开，对每一个参数和每一个可能抛出的错误问一句：「这个决定，凭什么要调用方来做？」 答不上来的，就是该你扛的。

贴进 code review 的话：「这三个参数（容量、重试间隔、批大小）用户基本不可能比我们算得准，填错还不会报错、只是悄悄变慢。能不能模块内部算出默认值，只保留确实需要外部决定的那一个？——模块应该完整地解决问题，而不是把难题外包给调用方。」
