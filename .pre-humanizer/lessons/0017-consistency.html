一致性

一致性是唯一一种「不写代码就能减少代码」的技术。它买到的东西是认知杠杆：看懂一处，等于看懂所有同类处。而它最贵的失败不是风格不统一，是两件不同的事长得一样——那会把读者的每一次合理推断都变成一次赌注。

17.1一致性买的是什么

第 17 章 · 开篇

一致性是降低系统复杂性、让行为更明显的一个强大工具。如果系统是一致的，就意味着相似的事以相似的方式完成，而不同的事以不同的方式完成。一致性创造了认知杠杆：一旦你懂得了某一处怎么工作，你就可以用这份知识立刻理解其他用同样方式做的地方。

一致性减少错误。如果系统不一致，两种情况可能看起来一模一样，实际上却不同。开发者看到一个眼熟的模式，就基于以前遇到的那个模式做出了错误假设。反过来，如果系统是一致的，基于"看起来眼熟"所做的假设就是安全的。

这段话里有两个断言，第二个比第一个值钱得多。第一个断言说的是效率：省下重新理解的时间。第二个断言说的是正确性：一致性让"凭直觉推断"这件事变得可靠，而不一致让每一次直觉推断都变成一次小赌博。

对你的三个痛点来说，一致性的位置很特殊：

  • 对「改一处怕漏」：一致性不直接减少改动点，但它让你能用搜索代替记忆。如果所有"取当前时间"的地方都叫 now_ms()，那 grep now_ms 就是一份完整的改动清单；如果有三种写法（clock()、gettimeofday、std::chrono::steady_clock），你的清单就永远不完整。
  • 对「评审说不出所以然」：一致性给了你评审里最硬的一句话——「这个仓库里其他 11 处都这么做，这一处没有」。它不需要你论证哪种更好，只需要你指出不一致。
  • 对「越拆越乱」：一致性是拆分的粘合剂。两个模块如果遵守同一套约定，它们之间的边界才可预测；否则每次跨模块调用都要重新确认对方的语义。

17.2一致性可以施加在哪些层面

书里列了五个层面，从最表面到最深刻。前两个几乎免费，后三个才是真正省钱的。

层面C/C++/Rust 里的样子不一致的代价
名字 size() / length() / count() 三种都表示"元素个数" 每个新人都要问一遍"这俩有什么区别"，答案通常是"没有"
编码风格 大括号位置、#include 顺序、const 放左还是放右 低。几乎全部可以交给 clang-format/rustfmt 消灭
接口 所有 Reader 都提供 read() 返回 Result<size_t>，0 表示 EOF 高。学会一个实现就能看懂其余同类，这是复用真正发生的地方
设计模式 仓库里所有异步都走同一套 Reactor + Handler 回调 高。读者认识这个形状，就能跳过对控制流的逐行推理
不变量 「每行以 \n 结尾」「所有 offset 都相对文件头」「所有 buffer 8 字节对齐」 最高。不变量每少一条，代码里就多一类特殊情况要处理

「不变量」这一行值得单独讲，因为它最不像"风格问题"，收益却最大。一个不变量是某个结构永远成立的性质。它的作用是：让读者可以在任意一行代码上原地推断，而不必回溯这条路径是从哪进来的。

// 不变量：lines_ 中的每个元素都以 '\n' 结尾，
// 且任意元素内部不含 '\n'。因此 split 只需按元素取，
// 拼接时不需要再补分隔符。
std::vector<std::string> lines_;

有了这条不变量，所有使用 lines_ 的代码都不需要再判断"最后一行有没有换行符"。没有它，这个判断会出现在五个地方，而且其中三个会写错。不变量的一致性，就是"同一件事在每一处都以同样的方式成立"。

17.3反例：同一个仓库里的两套错误处理

反例：三种失败语义，同一个模块

这样写 
// 版本 A：返回负 errno，0 表示成功
int write_block(uint32_t id,
                const void* buf, size_t n);

// 版本 B：返回 bool，错误码走输出参数
bool read_block(uint32_t id,
                void* buf, size_t n,
                int* err);

// 版本 C：返回长度，失败返回 -1
ssize_t sync_block(uint32_t id);
为什么烂

三种形态各自都合理，凑在一起就是灾难：

① 调用点必须逐字回查。写完 if (read_block(...)) 你要停一下：true 是成功还是失败？——这个问题在同一个文件里问了三次，每次答案不同。

② 错误处理无法统一。你没法写一个通用的重试包装，因为"怎么判断失败"有三种。于是重试逻辑被复制三份，其中一份漏了 EAGAIN 需要重试这个分支。

③ 变更会漏。要加一个新错误码 E_BUSY，你得改三处判断，bool 那版还会把它折叠成 false——信息在那一层就丢了，上层永远不知道是忙还是坏。

④ 最糟的：它们看起来一样。三个函数名都是 xxx_block、都接受 block id，读者的模式识别会给出错误答案。

改法不是"统一成最好那个"（那要改所有调用点），而是先把出口统一，再逐块迁移。这个仓库的 C++ 部分可以只用一条约定：

// 所有块 I/O 都返回 Status；status.ok() 为真时
// out 参数有效，否则 out 不被修改。
struct Status {
  int  code = 0;                 // 0 = 成功，否则为 errno
  bool ok() const { return code == 0; }
  explicit operator bool() const = delete;  // 禁止 if (s) 的歧义
};

Status write_block(uint32_t id, std::span<const std::byte> buf);
Status read_block (uint32_t id, std::span<std::byte> out);
Status sync_block (uint32_t id);

explicit operator bool() = delete 是个小技巧但很值：它让"顺手写成 if (status)"编译失败，逼调用点写出 if (st.ok())。这就是把一致性从人的记忆里搬进编译器——下一节讲的就是这件事。

17.4让约定活下来：三件工具

书里说得很直白：一致性很难维持，尤其是很多人长期做一个项目的时候。有人不知道别的组定下的约定，新人不知道约定，于是无意中违反约定，并且造出与既有约定冲突的新约定。它给了三个手段，按可靠性排序：

第 17 章 · 建立并保持一致性

文档。写一份文档，列出最重要的总体约定，比如编码风格指南，放在开发者会看到的地方（比如项目 Wiki 的显眼处）。鼓励新成员阅读它，也鼓励老人不时回顾。而对于更局部的约定，比如不变量，要在代码里找到合适的位置把它们记下来。如果你不把约定写下来，别人就不太可能遵守它。

执行。即使有好的文档，开发者也很难记住所有约定。落实约定最好的办法是写一个检查违规的工具，并确保代码在通过检查之前不能提交进仓库。自动检查器对低层次的语法约定尤其有效。

书里配了一个极好的真实案例：一个项目长期受行尾符折磨——Unix 上的人用 \n，Windows 上的人用 \r\n，编辑器会悄悄把整个文件的换行符换掉，于是每次小改动都表现为"整个文件被改"。约定写了、也说了，还是不断有人违反，每个新人来都要重新踩一遍。最后解决方式是一个提交前的脚本：发现被改动的文件里含 \r 就中止提交。问题一次消失，而且顺带完成了新人培训。

这个案例的模式可以复制到任何低层约定上。你的拦截钩子里值得放的三类检查：

  1. 可以用 grep 判断的。提交的 diff 里出现 std::endl（而不是 '\n'）、出现 new 、出现 reinterpret_cast 而不带 // why: 注释——全部可以几行 shell 拦住。成本最低，命中率最高。
  2. 需要语义判断的，用编译器。上面那个 explicit operator bool() = delete 就是这一类：你不用写检查脚本，C++ 本身就是检查器。同类还有 [[nodiscard]]、enum class（禁止隐式转 int）、std::span（禁止退化成裸指针+长度两个参数）、Rust 的 newtype（禁止把 FileId 传给要 BlockId 的地方）。
  3. 需要跨文件知识的，用测试或生成。「每个 `enum class` 值都要有一份字符串表」这种约定，可以写个静态断言，或者干脆从一份源定义生成枚举和字符串表。生成器是最高级的一致性：它让不一致在物理上不可能发生。

一个判据：如果一条约定只能靠"记得"来维持，它就不是约定，是愿望。约定要么写进文档且有人读，要么写进工具且拦得住人。能拦住的才算数。

第三件工具是代码评审，书里给了它一个不太客气但准确的定位：评审者越挑剔，团队里所有人学会约定的速度就越快。这句话的另一面是——如果你的评审只说"风格问题，不重要"，那约定就永远不会被学会。

17.5在罗马时：三条最常被违反的规则

书里用了那句老话：在罗马，就像罗马人那样做。改成操作性的三条：

第 17 章 · 在罗马时

处理一个新文件时，先环顾四周，看看既有代码的结构：公共变量和方法是不是都声明在私有成员之前？方法是按字母序排的吗？变量用 camelCase 还是 snake_case？当你看到任何看起来像约定的东西，就遵循它。做设计决策时，问自己项目里别处是不是做过类似的决策；如果是，就找一个现成的例子，在新代码里用同样的做法。

不要改变既有约定。抵制「改进」既有约定的冲动。有一个「更好的主意」并不足以成为引入不一致的充分理由。你的新想法可能确实更好，但一致性本身的价值，几乎总是大于一种做法胜过另一种做法的价值。

第二条是最难的，因为它要求你在明知道自己对的时候让步。书里给了两个可以公开讨论的问题，用来判断该不该推翻旧约定：

  1. 你手上有没有大量新信息，是当初建立旧约定时不存在的？「我觉得 Result 比错误码好看」不是新信息；「我们三年前上 C++17 了，现在有 std::optional 而当时没有」是。
  2. 新做法值得把全部旧用法都更新一遍吗？如果答案是"只改新代码，旧代码不动"，那这不是改进约定，这是制造第二套约定——比维持旧约定更糟，因为读者从此必须同时懂两套。

如果两个答案都是"是"、而且组织同意了，那么正确的做法是全量迁移，做完之后不留旧约定的痕迹。半迁移是所有选项里最坏的：它同时继承了两种约定的成本，却只拿到一种的收益。

对「改一处怕漏」这个痛点，这一段有个极实用的推论：当你不确定该用哪种写法时，去仓库里搜一个现成的同类，复制它的形状。这一步花 30 秒，省掉的是评审里的一轮往返，以及未来"两种写法并存"的永久维护成本。

17.6走得太远：不同的事必须长得不同

一致性最容易被误用的地方在这里。书里那句定义其实有两个方向，大多数人只记住了第一个：

第 17 章 · 走得太远

一致性不仅意味着相似的事应当以相似的方式完成，也意味着不同的事应当以不同的方式完成。如果你对一致性过于热衷，试图把不同的事强行套进同一个模子——比如给确实不同的东西用同一个变量名，或者把不适合某个模式的任务硬套那个模式——你制造的只会是复杂性和混乱。

一致性只有在开发者能够确信「如果它看起来像 x，那它确实是 x」时，才会带来好处。

最后那句话是整章最锋利的一句，它给了你一个反向检查清单：凡是你让两个东西长得一样的地方，问一句——它们真的是一回事吗？常见的三种强行统一：

  • 同一个变量名表示两个概念。第 14 章的经典事故：block 既指文件逻辑块号又指磁盘物理块号。为了"命名一致"，两件事共用一个词，结果是一次数据损坏。
  • 同步和异步路径塞进一个接口。为了"只有一种调用方式"，让 read() 有时阻塞有时不阻塞——读者从此无法从签名推断它会不会卡住线程。
  • 硬套设计模式。给一个只有两个状态的开关套上完整的 State 模式，六七个类。模式本身没错，错在把"不同的事"（简单状态 vs 复杂状态机）做成了同一个形状。

判断标准可以反过来用：一致的目的是让读者的推断可靠。如果你为了让形状统一，反而让某个推断变得不可靠了，那这次统一就是负收益。

练习这是一致性，还是过度统一

五个场景。判断它是「好的一致性」、「过度统一」，还是「该统一但没统一」。

仓库里所有 enum class 都配套一个 to_string()，且都由同一个 X-macro 生成枚举和字符串表。

这是最高级形态：不一致在物理上不可能发生。加枚举值时忘了加字符串这件事，被生成器消灭掉了——不用记、不用查、不用评审提醒。这类约定值得主动去找。

为了"接口统一"，让 FileReader::read() 和 SocketReader::read() 都返回 Result<size_t>，且都保证"返回 0 表示 EOF"；但 socket 的 0 其实是"对端关闭"。

形状统一了，语义没有。读者看到 Result{0} 会按文件语义理解成"正常读完了"，而在 socket 上这意味着对端断了、后续写入会失败。这违反 17.6 那句判据：看起来像 x，其实不是 x。正确做法是让两者长得不一样——比如 socket 用一个独立的 Eof 之外还要暴露连接状态。

同一个 .cpp 里，一半函数用 int 返回码，一半抛 std::system_error，因为"这两批代码是不同时期写的"。

这就是 17.3 那个反例的现场。它直接制造你的痛点①：任何跨这两批代码的改动，都要同时处理两种失败路径，而"哪些函数属于哪批"只能靠记忆或逐个读实现。至少要在文件头写清边界，更好的做法是先统一出口类型再逐块迁移。

新写的代码里，作者把 sockaddr 相关的转换写成 to_sockaddr_in()；仓库里既有的 12 处都叫 make_sockaddr()。

典型的"在罗马时"失守。而且它成本极低——改名只需一次重命名。这类问题最该在评审里当场说，因为新名字一旦合进去，就有了 13 处两种写法，再改就要说服更多人。

仓库里所有缓冲区都保证 8 字节对齐，这条不变量写在 Buffer 的类注释里，并且 alloc() 里有 assert 守着。

这是不变量型的一致性，收益最高：下游所有 memcpy、SIMD 载入、reinterpret_cast 都不必再考虑未对齐路径。注意它同时满足两个条件——写下来了（在类注释里），而且有人守（assert）。缺任一条，它半年后就不成立了。

练习把这个约定变成拦得住的工具

你的团队有个约定：「所有对外暴露的 struct 里，表示时间的字段必须带单位后缀（_ms / _ns / _s）。」这条约定写在 Wiki 上，半年内被违反了 7 次，其中两次导致把秒当毫秒的线上事故。

用 17.4 的三类工具，各给一个具体做法。重点：哪一类最划算？

① grep 类（最便宜，但只能拦住一半）：在提交钩子里扫 diff 新增的 struct 成员声明，匹配形如 (int|int64_t|uint32_t|long)\s+\w*(time|timeout|delay|interval|ttl|age)\w*\s*; 的行，如果变量名不以 _ms/_ns/_s/_us 结尾就报错。缺点：靠正则猜语义，会漏也能误报。

② 编译器类（最划算）：把"裸数字表示时间"这件事从类型系统里消灭掉，用强类型包一层：

// 不同单位的时长是不同类型，不能互相赋值
template <class Tag>
struct Duration {
  int64_t v;
  explicit constexpr Duration(int64_t x) : v(x) {}
};
using Millis = Duration<struct MillisTag>;
using Micros = Duration<struct MicrosTag>;

// 唯一允许的跨单位转换，必须显式写出来
constexpr Micros to_micros(Millis d) { return Micros{d.v * 1000}; }

struct Timeout {
  Millis connect;   // 单位在类型里，名字可以随意
  Millis read;
};

现在 Timeout{Micros{500}} 直接编译失败，命名约定的违规变成了编译错误。而且它顺带解决了 7 次违规背后真正的问题：读者不需要靠后缀来推断单位。

③ 生成类（这里不适用）：如果字段定义本来就在某个 schema 里（protobuf、IDL、表定义），那从 schema 生成结构体，并在生成器里强制单位类型，是最彻底的。但如果这些 struct 是手写的，为它引入一套生成器就过度了。

结论：②最划算。① 作为兜底值得加（十分钟的活），但它的定位是"防住还没迁移的老代码"；真正的修复是让裸 int64_t 不再能表示时间。命名约定治的是症状，类型治的是病。这也解释了为什么 Wiki 上的约定会被违反 7 次——靠命名的约定，只能靠记得。

顺便注意一个信号：一条约定被违反 7 次，通常不是因为团队不认真，而是因为它没有可执行的入口。这本身是设计问题，不是纪律问题。

练习一句话评审

能直接贴进 MR 的话：「这里新加了 read_block，返回 bool + 输出参数错误码。但仓库里另外 11 处块 I/O 都返回负 errno / 0 表示成功（write_block、trim_block 等都是）。同一个文件里两种失败语义并存，调用点必须逐个回查签名——我建议这次就跟既有约定走；如果你确实觉得 bool 更好，那值得单独开一次全量迁移，把 12 处一起改掉，而不是让两种写法长期共存。」

这句话的结构可以复用到任何一致性评审上：指出新写法 → 指出既有的 N 处反例（给数字）→ 说明不一致的具体代价（调用点必须回查）→ 给出两条路（跟随 or 全量迁移），并把"半迁移"明确排除。最后一步是关键：它让讨论从"你觉得哪个好"变成"你选哪条路"，而两条路都不会让仓库烂掉。
