通用模块更深入

每个新模块都面临同一个岔路：接口照着「今天要用的场景」刻，还是照着「这个东西本质上能做什么」刻。选错了，你会在三个地方付出代价——而且都不是性能。

6.1两个都很有道理的立场

先说清楚这道题的难点，否则很容易把它当成一句口号背下来。

立场 A：做得通用一点。实现一个能解决一类问题的机制，而不只是解决今天这个问题。这样将来发现新用途时，你已经写好了。这是第 3 章「投资」的思路：现在多花点时间，以后省回来。

立场 B：只做今天需要的。软件的未来需求很难预测，通用方案里会塞进永远用不上的功能；而且太通用可能就解决不好眼前的具体问题。将来真需要了，再重构也不迟。这是增量开发的思路。

两边都站得住。书里给的答案是第三种，而且关键在于它对这两个词做了不对称的处理：

第 6 章 · 有点通用的模块

最有效的办法，是以某种通用的方式实现新模块。「有点通用」（somewhat general-purpose）是指：模块的功能应当反映你当前的需求，但它的接口不应该反映你当前的需求。接口应当足够通用，以支持多种用途；同时又要让今天的需求用起来很方便，而不是跟今天的需求死死绑在一起。

「有点」这两个字很重要：别忘乎所以，造出一个通用到连当前需求都很难满足的东西。

把这句话拆成两条可执行的判据：

  • 功能层面可以专用。你只实现今天真正需要的行为——不做「将来也许有用」的提前量。
  • 接口层面必须通用。接口上出现的是这个模块能做什么，不是调用方今天打算拿它干什么。

注意这不是折中，是分层：功能收窄、接口放宽。下面用一个具体的缓冲区把这个区别摆出来。

6.2专用接口长什么样

设想你在写一个编辑器内核，其中管文本的模块叫 TextBuffer。很自然的一种写法是：先把 UI 上会发生的事列出来，然后一件一件给它配方法。

// 专用：把「用户按了什么键」翻译成缓冲区的方法
class TextBuffer {
public:
    void backspace(Pos cursor);                    // 删光标左边一个字符
    void delete_forward(Pos cursor);               // 删光标右边一个字符
    void delete_selection(Pos begin, Pos end);     // 删选区
    void delete_line(size_t line_no);              // 删整行
    void paste_at_cursor(const Clipboard& cb);     // 粘贴
    // ……再加七八个，一共十几个公开方法
};

写的时候感觉特别顺：UI 那边一个按键对应一个方法，实现起来直白，甚至看起来「封装得很好」——毕竟调用方不需要知道字符是怎么存的。

但它有三个问题，而且都会在半年后变成事故：

  1. 变更放大（痛点一）。产品说「粘贴后自动缩进」，这不是一个新按键，而是一个新组合。你得在 TextBuffer 里再加一个方法，或者改 paste_at_cursor 的语义——而它已经被别处调用了。改一个需求动两处，且第二处不在需求里。
  2. 方法多而浅。每个方法只服务一个 UI 动作，很多方法全项目只有一个调用点。缓冲区这个本该「深」的模块，被摊成了一排薄薄的壳。
  3. 信息泄漏（后门泄漏）。Clipboard 这种 UI 概念出现在了缓冲区的方法签名里；delete_selection 意味着缓冲区知道「选区」是什么——可选区是视图层的概念。缓冲区从此和 UI 绑死，两边都不能独立演化。

专用接口的病灶不在「方法多」，而在于它把调用方的词汇表抄进了被调用方的接口。一旦抄进去，调用方的每一次变化都会顺着接口传下来。

6.3通用接口：只看「这个东西本身能做什么」

换一个起点。不要问「UI 会怎么用它」，而问「一个文本缓冲区本质上提供什么能力」。答案短得惊人：

struct Pos { size_t line, col; };   // 位置是通用类型，不是游标

class TextBuffer {
public:
    // 在任意位置插入任意文本（可以含换行）
    void insert(Pos at, std::string_view text);
    // 删除 [from, to) 之间的所有字符
    void erase(Pos from, Pos to);
    // 返回与 p 相距 n 个字符的位置，跨行自动跳，负数向前
    Pos  adjust(Pos p, std::ptrdiff_t n) const;
    // 从 from 开始找下一次出现
    Pos  find_next(Pos from, std::string_view needle) const;
};

四个方法。UI 那边的事一件都没有，但每一件都能表达出来：

// 退格
buf.erase(buf.adjust(cur, -1), cur);
// Delete 键
buf.erase(cur, buf.adjust(cur, 1));
// 删选区：选区就是两个位置
buf.erase(sel.begin, sel.end);
// 删整行：整行也就是两个位置
buf.erase({line_no, 0}, buf.adjust({line_no, 0}, width_of_line));

现在「粘贴后自动缩进」这个需求落在哪？落在 UI 层的一小段代码里：先 insert 文本，再对每行 insert 缩进。缓冲区一行都不用改。这就是痛点一的解：新需求落在上层，不落在接口上。

短了一点，也长了一点

诚实地看：用通用接口实现「退格」的代码，比 buf.backspace(cur) 长。但可读性反而更好——读 UI 代码的人能不能一眼看出退格删的是哪个字符？能，因为闭区间就写在那里。而在专用版本里，他得跳进 TextBuffer 的实现（或它那份可能过期的注释）去确认。

第 6 章 · 错误的抽象

专用版本里的 backspace 方法是一个错误的抽象。它本意是隐藏「到底删掉哪些字符」的信息，可用户界面模块确实需要知道这件事。UI 开发者很可能会去读 backspace 的实现，只为了确认它的精确行为。

软件设计最重要的元素之一，就是判断谁需要在什么时候知道什么。当某个细节很重要时，最好让它显式、尽可能明显；把它藏在接口后面只会制造晦涩。

这句话值得停一下。第 5 章反复讲「藏起来」，这里却在说「别藏」。两者不矛盾：该藏的是实现决策，不是语义。退格的精确语义是调用方必须知道的契约，把它藏进别人的实现里，只是把知识从看得见的地方搬到了看不见的地方。

6.4通用接口为什么反而更简单

书里说这是通用方案最重要、也最令人意外的收益：它即使只被用于最初那个用途，也更好——因为接口更简单、模块更深。理由有三条，都在上文的例子里：

收益专用接口通用接口
方法数量 十几个，每个一个用途 四个，每个覆盖多个用途
认知负荷 新人要学十几条规则 学四条，其余靠组合
可测试性 要构造 Clipboard、Selection 等一堆类型 只需要 Pos 和字节串，测试极轻

第三行对底层读者尤其重要。通用接口的边界上只有「位置 + 字节」，这意味着你的单元测试不需要 mock 任何东西；而专用接口每加一个 UI 概念，就给测试加了一个必须伪造的依赖。测试伪造依赖的成本，最终会变成「这块代码没人敢改」。

反例

这样写 
// 缓冲区替 UI 决定了「粘贴」是什么
class TextBuffer {
public:
    void paste(const Clipboard& cb);
    void cut_selection();
    void indent_block(size_t line);
};
为什么烂

① Clipboard 是 UI 类型，缓冲区从此依赖 UI 的头文件；② 剪切 = 复制 + 删除，而「复制」的形态由 UI 决定，缓冲区不该管；③ 想支持「粘贴为纯文本」「粘贴并转义」，每来一个就得改一次缓冲区（变更放大）；④ 想给命令行工具复用这个缓冲区，得先伪造一个 Clipboard。

根源：这三个方法的参数，一个都不描述文本，只描述用户操作。

改法：缓冲区只留 insert / erase / adjust；剪贴板、缩进策略、撤销点全部留在 UI 层。如果发现 UI 层到处在重复同一段「取出剪贴板文本、逐行加缩进、insert」，那说明缺的是一个 UI 侧的辅助函数，而不是缓冲区的方法。

6.5三个自检问题

「有点通用」的度不好一次拿准。书里给了三个问题，可以直接在评审时问：

问题一：满足我当前全部需求的最简单接口是什么？

如果减少方法数量而不损失能力，你多半正在变通用。但不能靠加参数硬减：三个方法各带八个参数，那不叫简单。

问题二：这个方法会被多少种情况用到？

专门为一个用途设计的方法（比如 backspace）是红旗。看看能不能用若干个通用方法替换掉几个专用方法。

问题三：这个接口对今天的需求还好用吗？

这一问防的是走太远。如果你为了用上这个类，得在外面写一大堆胶水代码，那接口没提供对的能力。

走太远的那个经典例子

书里用它来标定边界：把文本操作做到单字符粒度——insert_char 和 erase_char，一个字符一个字符地加、一个字符一个字符地删。接口确实简单，也确实通用，但用它实现一个编辑器，上层会充满循环；插入一兆字节要调用一百万次，性能也不可接受。

所以答案不是「越通用越好」，而是：通用到「字符区间」这一级，停。区间的粒度既覆盖了所有编辑操作，又不至于把循环推给每个调用方。判断标准始终是：这一层的调用方，用起来是否自然？系统整体是否更简单？

6.6和底层读者的关系

这一章听起来像「接口设计美学」，但在 C/C++/Rust 项目里它有个非常具体的经济后果，值得单独说。

专用接口会把你的实现决策暴露成 ABI。一旦 TextBuffer::backspace(Pos) 被三个库用上，它就成了稳定接口；你想换成 rope 存储、想支持并发编辑，都得保证这十几个方法的语义不变。而通用接口只有四个方法，未来换实现时要维持的契约小得多。

通用接口更容易做成零成本抽象。一个 insert(Pos, string_view) 在内部可以是 memmove、可以是 piece table、可以是 rope；而 paste(const Clipboard&) 强制你在接口上接收一个具体类型，泛型化或内联化的空间都被堵死了。

通用接口更少成为 hot path 上的阻碍。底层代码在意「能不能批量」。区间接口天然支持批量（一次 erase 掉 4KB），单动作接口（backspace）则把批量能力锁在实现里，调用方无法表达。

练习判断这颗接口的病灶

四个片段。每一段判断它属于哪种问题——注意有时答案是「没问题」。

一个 HttpConn 类提供 read_request()，而它内部包着的 Socket 也提供 read_request()，方法体只有一行转发。

两层的抽象完全一样，中间那层不加功能只加认知负荷——这是第 7 章的透传方法，在这里先埋个伏笔。修法通常是让调用方直接用 Socket，或把职责合并。

一个 RingBuffer 只提供 push_slice(&[u8]) 和 pop_slice(&mut [u8]) -> usize，不提供按元素读写的接口。

区间粒度正好：既能表达单字节，也不会把循环推给调用方，而且天然支持批量与零拷贝。这是「有点通用」的正面样本。

一个 Config 要求调用方传 page_size、prefetch_pages、flush_interval_ms 三个值，而它们都能从设备探测出来。

它不是「太专用」，而是把决定权推给了调用方——第 8 章会专门讲这个（配置参数）。真正该通用的是接口形状，不是把每个内部策略做成旋钮。

一个 read_exact(fd, buf) 在读到 EOF 时返回错误码，四个调用点各自处理一遍「读少了怎么办」。

「读了但不够」是正常情况，不该是异常。让它返回实际字节数（0 表示 EOF），四个调用点的分支就都消失了——第 10 章「通过定义规避错误」。

练习改写一个接口

你接手一个 LogWriter，它提供 write_info(msg)、write_warn(msg)、write_error(msg)、write_debug_kv(k, v)、write_request_line(conn)。日志格式（JSON lines）在五个方法里各写了一遍。请用第 6 章的视角重写它。

提示：先问「这个模块本质上在做什么」，而不是「谁会调用它」。

本质能力只有一件事：把一条带级别的结构化记录序列化并写到目标。级别不是五种方法，是一个参数；字段不是 _kv 特例，是记录的一部分。

enum class Level { Debug, Info, Warn, Error };

struct Field { std::string_view key, value; };

class LogWriter {
public:
    void write(Level lvl, std::string_view msg,
               std::span<const Field> fields = {});
};

五个方法塌成一个。write_request_line(conn) 的职责回到调用方：它在自己那一层把连接信息拼成 Field——因为「一次请求该记哪些字段」是业务知识，不是日志模块的知识。

收益是具体的：改日志格式只动一处；加一种级别只改枚举；要加「采样」「脱敏」，都落在 write 内部，五个调用点一个都不用动。反过来，如果业务方需要「请求日志特殊格式」，那是它自己的辅助函数，不该进 LogWriter。

一个诚实的补充：如果只有一个调用点、格式一周后才定，那么保留 write_info 这类薄封装也无可厚非——判据是「有几个使用者、变更有多大」，不是「通用永远更好」。

→带走什么

这一章其实给了一个可以立刻用的动作：打开你的模块头文件，把公开方法按「它描述的是调用方的动作还是模块的能力」分成两列。第二列通常短得多，而第一列里的每一条，都是一个还没发生的变更放大。

贴进 code review 的话：「这几个方法描述的是调用方的动作，不是这个模块的能力——`backspace`、`paste`、`delete_selection` 都是 UI 词汇。能不能把接口收到 `insert(pos, text)` / `erase(from, to)` 这一级，把按键语义留在调用方？」
