复杂性的症状与成因

第 1 章给了方向，这一章给尺子：复杂性有三个可观察的症状，两个可切除的成因。

2.1定义：实用性优先

复杂性是任何使系统难以理解和修改的东西。

第 2 章

这个定义有三个刻意的选择：

  • 与规模无关。小系统也可以很复杂，大系统也可以很清晰。
  • 与功能无关。功能少不等于简单。
  • 是开发者的体验，不是代码的属性。它随时间、随人变化。
第 2 章 · 什么是复杂性

复杂性是开发者在某个时间点、试图完成某个具体目标时感受到的东西，它不必与系统的整体规模或功能挂钩。人们常用「复杂」描述功能繁多的大型系统，但只要这样的系统容易使用，按本书的定义它就不复杂。反过来，小而简单的系统也可能非常复杂。如果一个软件系统难以理解和修改，它就是复杂的；如果容易理解和修改，它就是简单的。

作者还给了一个粗略的加权公式：C = Σ cp × tp——每个部分的复杂程度，乘以开发者花在它上面的时间。含义是：没人碰的复杂代码，代价小；天天改的复杂代码，代价大。

第 2 章 · 用加权看待复杂性

复杂性取决于最常发生的活动。如果系统里有几块极其复杂的部分，但几乎没人需要碰它们，那它们对整体复杂性影响不大。粗略地用数学刻画：系统的总体复杂度 C，等于每个部分的复杂度 cp 乘以开发者花在该部分上的时间 tp 的加权和。把复杂性隔离在一个永远不会被看到的地方，几乎和彻底消除它一样好。

这条对底层代码格外重要。一个 80 行的 SIMD 快路径，如果三年只改过一次，它的「cp」很高但「tp」约等于零，不值得为它牺牲可读性去炫技。反过来，那个被每个 .c 文件 #include 的头文件，哪怕只多了一个语义含糊的宏，它的 tp 是全体工程师的全部工时——那个才要盯。

判定权的转移：复杂与否，由读者判定而非作者。如果你觉得一段代码难以理解，那它就是复杂的——作者说「这很简单」不构成反驳。这条规矩在代码评审里极其好用。

作者把这个判定权讲得很明确：对自己写的代码觉得简单，别人觉得复杂，那么它就是复杂的；这时候该做的是去问对方为什么觉得复杂，因为「你的视角」和「他的视角」之间的差距里，往往藏着有价值的东西。开发者的职责不只是写出自己能轻松使用的代码，还要写出别人也能轻松使用的代码。

2.2三个症状

症状你会看到什么书里的例子
变更放大
change amplification		 一个看起来简单的改动，要在很多地方重复修改 网站 banner 背景色：每个页面硬编码 → 改成中心变量 bannerBg 后只需一处
认知负荷
cognitive load		 完成一个任务，需要先知道多少东西 C 里 allocate 之后必须由调用者 free——你写一行代码也得记住整条生命周期规则
未知的未知
unknown unknowns		 不知道该改哪里，甚至不知道这里有问题 某个页面的强调色没有跟着 bannerBg 变——你根本不会想到去检查

三者中最糟的是第三个。变更放大至少还会痛，痛了就会去找；认知负荷至少是可见的成本；而「未知的未知」是你连搜索的方向都没有。作者说得很绝：唯一能确定没有漏的办法是读完系统里的每一行代码，而这在任何规模的系统上都做不到，甚至读完了也不够，因为那个改动可能依赖于一个从未被记录下来的细微设计决定。

第 2 章 · 为什么未知的未知最糟

在复杂性的三种表现形式里，未知的未知是最糟糕的：它意味着你本该知道某件事，却无从找到它是什么，甚至无从知道问题的存在，直到错误已经发生。变更放大很烦人，但只要你知道该改哪些代码，改完系统就能工作；认知负荷会抬高改动的成本，但只要读哪些信息是明确的，改动仍然可能正确。面对未知的未知，你既不清楚该做什么，也无法判断方案是否有效。

症状一：变更放大在 C 项目里的样子

最经典的是「同一个常量被抄进多个编译单元」。真实一点的形态：一个报文头同时被发送端、接收端和抓包工具解析，三处各自 #pragma pack、各自算偏移。协议加一个字段，你要改三处，而且没有任何工具会告诉你第三处忘改了——它只会在某个版本的抓包文件里安静地错位。

注意变更放大至少有一个好处：它痛。痛可以被自动化。把常量换成 enum，把字段偏移换成 offsetof，把「必须同步」换成编译期 static_assert，痛就变成了编译错误——编译错误是我们能拿到的最便宜的保险。

症状二：认知负荷在 Rust 里反而更清楚

作者用 C 的 malloc / free 举例：一个函数分配内存、返回指针、并假定调用者会释放。你写一行调用，就得记住一整条生命周期规则；忘了就是泄漏。Rust 的 Result<T, E> 和所有权体系做的是同一件事的反面——把这条规则从「你要记住的知识」变成「编译器会检查的类型」。这不是说 Rust 不复杂，而是说它把一条隐性规则从认知负荷里搬走了。

同一个道理在 C++ 里是 RAII：std::vector<u8> 替你管生命周期，std::unique_ptr<FILE, decltype(&fclose)> 替你管 FILE*。你少记一条规则，认知负荷就少一分。

症状三：未知的未知，来自「一处改了、别处没跟上」

书里那个例子的结构值得原样记住：系统有了中心变量，看起来很容易改，但另一处手工指定的值必须跟着变，而没人知道它存在。 换成 C：页大小从一个宏改成了运行时查询，但某处 mmap 的对齐仍然写死 4096。改了宏，编译通过，测试通过，只在 ARM64 的 64K 页机器上崩。

常见误区

用代码行数衡量复杂性。行数多的实现，如果接口简单，可以是很低的复杂性；行数少的实现，如果读它要打开另外五个文件，复杂性很高。量的是「理解成本」，不是「文本体积」。作者还补了一句更狠的：他见过让应用只需几行代码就能写出来的框架，但那几行到底是什么，极难弄明白。有时写得更多反而更简单，因为它压低了认知负荷。

2.3两个成因

依赖 Dependencies

某段代码不能被孤立地理解和修改。改 A 必须先看 B。

→ 变更放大 + 认知负荷

晦涩 Obscurity

重要的信息不明显：名字太泛、单位未注明、关键约束只存在于某人脑子里。

→ 未知的未知 + 认知负荷

依赖不是纯粹的坏东西。作者特意说明：每次你写一个新类或一个新模块，都是在围绕它的接口建立依赖。目标不是消灭依赖，而是减少数量、让剩下的依赖尽量简单和明显。网站例子里，新的做法消灭了页面之间的互相依赖，却引入了对 bannerBg 的依赖——而这笔交易划算，因为新依赖是明显的、可搜索的、编译器能管的。

这条「划算的交易」对底层读者有直接的操作含义：如果你不得不在两个方案里选，选那个破坏时会编译失败的方案。

晦涩的三种典型来源

  • 名字不承载信息。time、size、buf、data——单独看等于没名字。
  • 单位/量纲没写。int timeout 是毫秒还是微秒？size_t len 是字节还是元素个数？读遍代码也可能看不出来，只能问作者。C 里这一点尤其致命，因为类型系统帮不了你。
  • 不一致。同一个名字在两处表示两件事，或者同一个概念在两处有两个名字。开发者无法确定某个变量到底指什么。

作者还有一句判断标准很好用：需要大量文档，往往是设计不对的信号。减少晦涩最有效的办法不是补文档，而是简化设计。

反例

这样写 
/* sensor.h —— 看起来封装了，其实全靠注释活命 */
struct sensor {
    int fd;
    unsigned rate;      /* 采样率 */
    unsigned reg;
    void *buf;
    size_t len;
};

int sensor_read(struct sensor *s, void *out, size_t n);
为什么烂

rate 的单位没写，reg 是什么寄存器没说，len 是 buf 的容量还是已填充长度？调用者必须先读实现才知道怎么填这个结构体——于是每个使用者都在自己脑子里维护一份「这个字段其实表示什么」的副本。这就是晦涩，它直接制造未知的未知。

sensor_read 返回 int，但没人知道失败时 out 有没有被写过、len 有没有被更新。调用方只能猜，猜错就是读到未初始化内存。

改法：把可变状态收进实现，接口只暴露调用者真正需要的两三个操作。比如 sensor_open(dev_path, hz)、sensor_read_blocking(s, out, cap) -> Result<size_t, errno_t>、sensor_close(s)；单位写进参数名（hz、timeout_ms），错误语义写进头文件注释并保证「失败时 out 不被写」。结构体字段从公开变成不透明指针。能藏起来的字段，就一个都不要露。

对照上一节的表：依赖解释前两个症状，晦涩解释后两个。这就是为什么消除复杂性只有两条路（第 1 章）——减少依赖（封装）和减少晦涩（让它显而易见）。

2.4它是增量累积的

这是本章最需要记住的一句：

复杂性不是由单个灾难性错误引起的；它是由成千上万个小的依赖和晦涩累积而成的。

推论有两条，都很不客气：

  1. 你不会在某天突然发现系统变复杂了，所以没有「该处理了」的报警点。
  2. 一旦累积起来，就很难再消除——因为清理本身也需要理解整个系统。

更麻烦的是心理层面：每一个单独的妥协都说得通。「这一次多加一个 #define 无所谓」「这一次多拷一份解析逻辑，赶时间」。如果每个开发者对每一次改动都这么想，复杂性就迅速堆起来了。而单独修掉一个依赖或一处晦涩，几乎看不出任何变化——所以清理永远排不上优先级。

所以第 3 章要给的不是技术，是一种态度：零容忍。

2.5把症状当成评审用语

三个症状真正好用的地方在于：它们是可命名的。评审时说「这段不太好」没人能接；说「这是变更放大，协议布局被抄进了三个编译单元」对方立刻知道要干什么。第三个痛点——评审说不出所以然——有一半就靠这套词汇解决。

你在评审里看到可以说建议
同一个常量出现在多个文件变更放大收进一个头文件，或改成函数查询
调用者必须记住调用顺序认知负荷 + 晦涩合并成一个调用，把顺序收进实现
需要读三个文件才能确定这里安全未知的未知把那段知识挪到一个模块里
函数名需要注释解释单位晦涩把单位写进名字或改类型

练习给它贴标签

下面四个场景，判断它主要属于哪个症状。别急着选「都对」——找出主导的那一个。

你把 struct peer 的 addr 改名为 endpoint，编译器报了 14 个文件的错。

一个概念性改动扩散到 14 个文件，就是变更放大的教科书形态。注意：编译器的报错其实是好事——它把「未知」变成了「已知」。

某个函数接受一个 int timeout。读遍代码也看不出单位是秒还是毫秒，只能去问作者。

你要完成任务，必须额外掌握一条不写在签名里的知识——这就是认知负荷。它同时也是晦涩（信息不明显），成因与症状在此重叠。

某个序列化函数在内部悄悄做字节序转换。你在另一处按同样方式调用，结果数值差了 256 倍，测试没覆盖到。

最典型的「未知的未知」：你不知道该去怀疑这里。没有报错、没有编译失败，只有一个安静的错误答案。

一个结构体有 12 个字段，6 个函数各自读写其中六七个字段。改一个函数前你得先看完全部 6 个。

问题是「一次要装进脑子多少东西」。行数不多也可能认知负荷极高——这正好证明了复杂性不等于代码量。

可以贴进 code review 的原话：「这里属于变更放大/未知的未知——同一个设计决策出现在多个地方。请把它收到一个模块里，让「改漏了」变成编译错误而不是线上事故。」
