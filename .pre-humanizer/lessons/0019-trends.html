软件发展趋势

这一章不教你新东西，它教你一件事：拿到任何流行做法，先问「它到底削掉了哪种复杂度」。六种趋势，六次过闸门。

19.1机制不等于设计

前面十八章讲的是原理，这一章讲的是「别人告诉你的最佳实践」。作者把过去三四十年最响的六个名字摆上台：面向对象与继承、敏捷、单元测试、测试驱动开发、设计模式、getter/setter。然后对每一个都问同一个问题——它是否真的降低了大型系统的复杂性？

这个问题之所以必要，是因为「流行」和「有效」之间没有因果关系。一个机制进入语言、进入教科书、进入面试题，只说明它被广泛采用，不说明它在你这个系统里降低了复杂度。作者的态度很直接，也是本章最该带走的一句：

每当您遇到有关新软件开发范例的提案时，就必须从复杂性的角度对其进行挑战：该提案确实有助于最大程度地降低大型软件系统的复杂性吗？

第 19 章 · 结论

下面这些，你大概每天都在用。但用得好不好，取决于你有没有认出它们的收益从哪来、代价从哪来。

接口继承一个接口适配多种实现，接口变深几乎没有——前提是父类不带状态

19.2继承的两副面孔

这一节是全章最有价值的部分，因为它把一个笼统的「继承好不好」拆成了两个东西，而这两者对复杂性的作用方向相反。

接口继承：父类只声明签名，不实现。C++ 里是纯虚基类，Rust 里是裸 trait。它的收益是本书对「深」的另一种算法：同一个接口的实现越多，这个接口越深。因为它必须只保留所有实现共有的本质，把差异全部挡在接口之外——这正是抽象的定义。

实现继承：父类不但给签名，还给默认实现，通常还带实例变量。它的收益是真的：几个子类不必重复同一段代码，于是「改一处」而不是「改五处」，变更放大被压下去了。

但代价也在同一处：父类的实例变量通常被父类和所有子类一起访问。

第 19 章 · 实现继承的成本

实现继承会在父类及其每个子类之间创建依赖关系。父类中的实例变量经常被父类和子类同时访问，这导致继承层次中的类之间出现信息泄漏，并使修改层次中的一个类时很难不考虑其他类。在最坏的情况下，程序员需要完全了解父类下的整个层次结构，才能对任何一个类做出修改。广泛使用实现继承的层次结构往往具有很高的复杂性。

注意这里的因果链：共享状态 → 信息泄漏 → 依赖 → 认知负荷。它和你在第 5 章学到的后门泄漏是同一个病，只是换了个位置：泄漏不在两个平级模块之间，而在一条继承链的上下之间。

作者给的两条对策，按优先级：

  1. 先用组合。把共享功能做成一个小辅助类，让原来的类各自持有一个（或按值内嵌一个），而不是从父类继承。功能一样共享，状态不再共享。
  2. 实在要用实现继承，就把父类管理的状态和子类管理的状态分开：某些成员只由父类的方法读写，子类只能读，或者必须经由父类的其他方法间接改。

对 C / C++ / Rust 读者的翻译

C++：带数据成员的基类 + 子类直接摸 protected 成员，就是标准的实现继承陷阱。protected 不是「内部」，它是对所有未来的子类公开的接口——一旦发布，你改不动它。

Rust：trait 只有接口继承，trait 的默认方法也不携带状态，所以 Rust 天然躲开了这个坑。代价是共享代码要靠 impl 块、泛型约束或组合来组织——这恰好逼你走「组合优先」那条路。

C：手写 vtable（函数指针表）是接口继承；把结构体第一个成员做成「基类」再强转，就是实现继承，而且连编译器的类型检查都没有——同一种泄漏，更隐蔽。

反例 · 基类的 protected 状态

这样写 
class Conn {
protected:
    int fd_;                  // 子类直接读写
    std::vector<uint8_t> in_;
    size_t consumed_ = 0;
public:
    virtual ssize_t fill() = 0;
    virtual ~Conn() = default;
};

class TlsConn : public Conn {
public:
    ssize_t fill() override {
        ssize_t n = ::read(fd_,
            in_.data() + in_.size(), 4096);
        if (n <= 0) return n;
        in_.resize(in_.size() + n);
        return decrypt(in_, consumed_);
    }
};
为什么烂

三个成员全是 protected，等于把「缓冲区怎么表示、游标怎么走」宣布成公开契约。想给 in_ 换成环形缓冲、想给 consumed_ 换成指针，都要改所有子类。

反过来，TlsConn 的 fill() 必须懂基类的缓冲区约定：resize 之后 data() 会不会失效、consumed_ 由谁推进。这是第 2 章的未知的未知——读 TlsConn 的人看不出它依赖了这些约定。

还有一个附带伤害：TlsConn 的测试必须构造出 Conn 的那套状态，没法单独测。

改法：让 Conn 只保留一个纯虚接口 fill(uint8_t* dst, size_t cap)，把「读 + 解密 + 游标」的实现下沉成一个独立的 ByteStream，由具体连接按值持有。这样共享的是代码，不是状态；改缓冲区表示只碰 ByteStream 一个文件。

19.3增量应该是抽象，不是功能

敏捷对本书是「部分兼容」。它最核心的那条——开发应该是渐进的、迭代的——和作者的主张一致：项目开始时没人能预见正确的设计，好设计只能靠一个个增量长出来。

但敏捷有一个被反复误读的副作用：它把注意力放在功能上，鼓励「先做能跑的最小版本，等真需要了再重构」。作者认为这实质上就是战术编程，会快速积累复杂度。他给的替代口径很短：

第 19 章 · 增量单位

渐进式开发通常是个好主意，但软件开发的增量应该是抽象，而不是功能。可以推迟对某个抽象的所有想法，直到功能真的需要它为止。一旦需要这个抽象，就要花一些时间做简洁的设计——遵循第 6 章的建议，让它具有通用性。不要在一段时间里零散地把抽象一块块拼出来，而应一次设计到位，至少覆盖一组合理完整的核心功能。

这句话直接对应你的第一个痛点：改一个需求要动好几处，怕漏。 为什么会长成那样？因为抽象是零散长出来的——第一版只支持文件，第二版加了个 if (is_socket)，第三版又加 if (is_mmap)。每加一个功能，你都要回到那个函数里再插一个分支。功能在增长，抽象从未被设计过。

正确的节奏是反的：功能可以拖延，抽象不能拖延。 你完全可以只实现「读本地文件」这一种情况，但在写下第一个字节之前，先花二十分钟想清楚「输入源」这个抽象该长什么样——它藏起什么、暴露什么、未来加 socket 时要不要改接口。二十分钟买的是后面三年不用动接口。

一句话：功能是消耗品，可以后补；抽象是地基，补不了。每次要「先写个特例、以后再说」的时候，先问自己：这个特例会不会变成接口的一部分？

19.4测试是重构的许可证

这一节在书里被低估了。作者说测试的作用不只是抓 bug，更是让重构变得可行：没有测试套件，对系统做结构性改动就是在赌命；赌不起，于是所有人都选择「尽量少改」，而设计错误就永久留在那儿。

他举了自己项目里的例子：Tcl 把解释器换成字节码编译器，几乎动了核心引擎的每一部分；因为有出色的单元测试套件，alpha 版发布后只出现了一个 bug。

对底层读者，这条尤其重要。C/C++ 代码库里最不敢动的往往是内存布局和所有权约定——因为改错就是段错误或数据损坏，而不是一个断言失败。这正是「设计错误得不到修正」的重灾区：明明知道这个结构体该拆，但没人敢拆。

所以单元测试的价值在本书框架里可以这样表述：它是把「修改的风险」压到可接受范围的工具，因而也是让第 3 章的战略投资能够落地的前提。 没有它，那 10–20% 的设计时间根本花不出去。

19.5TDD：一个例外，而且是最好的例外

作者自称是单元测试的坚定拥护者，但对测试驱动开发不热衷。理由很干脆：TDD 把注意力锁在「让这个测试变绿」上，而任何时刻都很容易再写一个功能、再让一个测试变绿，于是没有一段时间是留给设计的。这是纯粹的战术编程。

第 19 章 · 修 bug 时先写测试

有一个地方先写测试是有意义的，那就是修 bug 的时候。在修复错误之前，先写一个因为该错误而失败的单元测试；然后修复它，并确认测试通过。这是确保你真的修好了这个错误的最好方法。如果你先修好了错误再补测试，新的测试很可能根本不会触发那个错误，于是它并不能告诉你问题是否真的解决了。

把它变成一句可以在评审里说的话：「这个 bug 的复现测试在哪？先让它红。」 这句话有两个作用：一是挡住「改了但没修好」，二是挡住「修好了但下次会再犯」。

19.6设计模式与 getter/setter：两种过度使用

设计模式本身没问题。它们之所以存在，是因为反复解决了同一类问题，而且通常给出了干净的解法。风险只有一个：过度使用。不是每个问题都该塞进一个现成的模式；当自定义解法更简单时，套模式只是给自己加了一层要读懂的东西。作者的原话是：使用设计模式并不会自动改善系统，只有在模式合适的时候才会。

他挑出来当反面教材的，是当年最流行的那一个：getter 和 setter。

论证是这样的：如果实例变量本来就不该公开，那么正确的做法是不公开，而不是给它配一对方法。getter/setter 通常只有一行，是标准的浅方法——它们在几乎不提供功能的情况下把接口撑大，同时把内部表示（字段名、类型、可变性）原封不动地写进了公开 API。所谓「以后可以加校验而不改接口」的收益，只在「你确实要公开这个变量」的前提下才成立；而大多数情况下你根本不需要公开它。

换成你熟悉的语言：

  • C++：int size() const { return size_; } 这种一行转发，如果外部只需要「大小」而不需要「那个成员」，更好的设计是让外部根本不需要问——比如提供一个 empty()、或者让遍历自己知道何时结束。
  • Rust：pub struct 的 pub 字段就是裸奔的实例变量；给它加 pub fn field(&self) -> T 只是换了个写法。真正的问题是：调用方拿这个值去干什么？如果答案是「自己算下一步」，那说明有一段知识本该在模块里。
  • C：结构体字段全是公开的，根本没有「藏」这个选项——所以 C 的做法是把不透明指针（struct Foo; + 操作函数）当接口，那才是真正的信息隐藏。

一句能贴进评审的话：「这个 getter 只是把字段念了一遍——调用方拿到它之后自己做了什么判断？那段判断应该搬进来。」

练习过闸门

四个场景，都在真实代码库里常见。判断它们属于哪种情况。

一个 Buffer 基类带着 capacity_、len_ 两个 protected 成员，五个子类各自实现 append() 并直接修改它们。

共享的不是接口，是状态。改 len_ 的表示要动五个子类，而且要保证五处的语义一致——这就是层次内的信息泄漏。改法：抽一个 ByteBuf 按值持有，或至少把状态改成私有 + 只读访问。

一个 struct Reader { virtual size_t read(uint8_t*, size_t) = 0; }，文件、socket、内存映射各有实现；接口里没有任何数据成员。

父类零状态、零默认实现，只有签名。三个实现越多，这个接口越深——这正是本书认可的「接口继承提供对抗复杂性的杠杆」。

团队按敏捷节奏两个迭代做完「导出 CSV」，第三个迭代做「导出 JSON」时复制了整个 Exporter，只改了序列化那二十行。

增量单位是功能，不是抽象。第二个格式出现的那一刻，Exporter 的接口（藏什么、暴露什么）其实已经被确定了，但没人去设计它，于是靠复制绕过。复制之后，改字段顺序要改两处。

修一个 mmap 越界读的 bug：于是先写一个在旧代码上必崩的测试，再改 map_len 的计算，最后确认测试通过。

书里点名的例外就是修 bug。先红后绿，保证你测的确实是那个 bug，而不是一个碰巧也过的测试。

练习改一段继承

你有一个 Parser 基类，带 protected std::vector<Token> tokens_ 和 pos_，派生出了 JsonParser、YamlParser、TomlParser。三个子类都在自己的 parse_value() 里推 pos_、读 tokens_。客户要加第四种格式。用第 19 章的视角，你该做什么？

提示：先别问「要不要加一层基类」。

先分清两个东西：token 流和游标是一个抽象，语法是另一个抽象。现在它们被同一个基类混在一起，于是三个子类都必须懂 tokens_ 的内部约定（末尾有没有 sentinel、pos_ 越界代表什么）。

  • 把 tokens_ + pos_ 收进一个按值持有的 TokenStream，接口是 peek()、next()、expect(kind)。三个子类从此只能通过这三个方法看输入，再也碰不到容器。
  • Parser 变成纯接口：virtual Node parse(TokenStream&) = 0;。零状态、零默认实现——这才是接口继承。
  • 三种格式共享的「错误恢复」逻辑，如果确实一样，做成自由函数或 TokenStream 上的方法，而不是基类的 protected 成员函数。

判据还是老一条：加第四种格式时，你希望只碰一个新文件。 如果实现完还要回头改基类，说明那个知识没藏好。

另外要诚实：如果三种格式的语法其实高度相似（比如都是 JSON 的超集），那更好的答案可能是一个解析器加配置，而不是三个类。这正是第 6 章「通用模块更深入」要问的问题——先问要不要拆，再问怎么拆。
