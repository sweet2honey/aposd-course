修改现有的代码

你 90% 的代码时间不是在写新模块，而是在别人写的函数里加一个分支。这一章讲的是那个时刻的判断标准：最小改动往往是最贵的改动，而「先让它跑起来」是一笔按天计息的高利贷。

16.1最小改动是最贵的改动

第 3 章把「战术编程」和「战略编程」分开了：战术编程的首要目标是"尽快让它工作"，哪怕代价是额外的复杂性。当时这条区分讲的是从零开始写东西。第 16 章把它搬到一个更难的地方——你正在改一段不是你写的、你并不完全信任的代码。

在这个场景下，几乎所有人都会滑向同一个念头：「我能做的最小改动是什么？」而且这个念头听起来还挺负责——改动小，风险小，不会引入新 bug，对吧？

第 16 章 · 保持战略性

不幸的是，当开发者进入既有代码去做修改（比如修 bug 或加功能）时，通常不会从战略角度思考。一个典型的心态是「我能做出的、满足我需要的最小改动是什么？」有些人觉得这很合理，因为他对要改的代码不放心，担心更大的改动意味着更大的引入新 bug 的风险。

但这正是战术编程。每一个这样的最小改动都会引入几个特殊情况、依赖，或者其他形式的复杂性。结果系统设计变得差了一点，而问题会随着系统演化的每一步累积起来。

「引入几个特殊情况」这句话值得逐字拆开看，因为它是本章所有诊断的根。一个战术补丁在 C/C++ 里通常长成这三种样子：

  • 多一个 bool 参数。void flush(bool force)。第二个需求来了，就变成 flush(bool force, bool sync)；第三个需求来了，你会开始考虑 std::bitset。每个调用点都要重新回答一遍"我该传什么"。
  • 多一个 if 分支，只有一处需要。于是某个函数里出现了一个「只有 A 路径会走」的分支，而它依赖一个「只有 A 路径才会设置」的成员。这条隐式的调用顺序不会出现在任何签名里——这就是第 2 章的未知的未知。
  • 多一个旁路。不动原函数，在旁边新写一个 flush_fast()，让它复制 60 行再改两行。从此「刷新」这件事有了两个真相，而它们会分叉。

三种形态的共同点是：改动本身很小，但它给系统留下的长期成本不小。这就是本章最反直觉的一句话——改动的大小和它造成的复杂度没有关系。一个两行的补丁可以让三个调用点从此必须遵守一条没写下来的规则。

评审时可以直接说的一句话：「这个补丁本身没问题，但它把一条新规则（调用方必须先 A 再 B）塞进了调用约定，而没有塞进类型或接口。下一个改这里的人不会知道这条规则。能不能让编译器替我们记住它？」

16.2完成的定义：像一开始就设计过

书里给了一个很高的标准，但它是本章唯一可操作的目标：

第 16 章 · 理想状态

如果你想为一个系统保持简洁的设计，那么在修改既有代码时就必须采取战略性的方法。理想情况下，当你完成每一次改动时，系统的结构应当和「你一开始就带着这个改动去设计它」所能得到的一样。

为了做到这一点，你必须抵制快速修复的诱惑。相反，你要根据这次想要的变化去重新审视：当前的设计是否仍然是最好的？如果不是，就重构系统，让最终得到的是可能的最好设计。按这种方式，系统设计会随着每一次修改而变好。

把这段话翻译成日常动作，就是三个问题，改代码之前按顺序问一遍：

  1. 这次改动，需要哪个模块多知道一件事？如果答案是"三个模块都要多知道一点"，那知识没有被藏好（第 5 章的信息泄漏），而这次改动正是一个把它收拢的机会。
  2. 改完之后，那个"多知道的一件事"是活在接口里，还是活在每个人的记忆里？活在记忆里的部分，就是下一次变更放大的种子。
  3. 有没有一个版本，成本只比补丁高一点点，但把这件事放进了类型系统？这几乎总是存在的，而且往往就在手边——一个 enum class、一个带默认值的结构体、一个 [[nodiscard]]。

注意第 1 个问题的措辞是「多知道一件事」，不是「多调一个函数」。前者是设计问题，后者是排版问题。绝大多数评审争论之所以说不出所以然，就是因为它停在"多调一个函数"这一层，而没人把它翻译成"多知道一件事"。

反例：三个重载养出来的调用约定

这样写 
// kv_store.h
int put(const std::string& key,
        const std::string& val);

// 第二个需求：要能设过期时间
int put(const std::string& key,
        const std::string& val,
        int64_t ttl_ms);

// 第三个需求：要能要求落盘后才返回
int put(const std::string& key,
        const std::string& val,
        int64_t ttl_ms, bool sync);
为什么烂

每一次加需求都是"最小改动"，三次之后：

① 三个重载，语义在名字上看不出来，新人得读三遍实现才知道 ttl_ms=0 是什么含义。

② 第四个需求（比如"压缩阈值"）来时，你没有第四个重载可加——参数已经四个了，只能再开一个 put_opt()。

③ bool 在调用点完全不可读：put(k, v, 5000, true) 里的 true 是"落盘"还是"不落盘"？调用点必须回查声明，这是纯粹的认知负荷。

④ 所有调用点是同时被牵动的：想给默认行为加一层校验，得改三个函数的实现，且必须保证三份逻辑永远一致。

改法：把「一次写入有哪些可选项」这件事收进一个结构体。加第四个选项时，旧调用点一个字都不用改。

// kv_store.h
struct PutOptions {
  int64_t ttl_ms = 0;      // 0 表示永不过期
  bool    sync   = false;  // true 表示返回前已落盘
};

// 写入一条记录；失败返回负的 errno，成功返回 0。
// 同一 key 的并发写入以最后落盘者为准。
int put(std::string_view key, std::string_view val,
        const PutOptions& opt = {});

这不是"设计得更漂亮"，而是把变化点从 N 个调用点挪到了 1 个结构体。前者是战术，后者是战略。差别不在代码量（新版还更短），在"下一次改需求要动几处"。

16.3保持在代码库现状之上，而不是顺势下滑

这一章有个隐含假设值得明说：你的改动会成为下一个人的"现状"。如果周边代码用裸 new/delete 管理生命周期，而你新加的路径也用裸指针——因为"跟周围保持一致"——那么六个月后清理的人要改的范围就从一个文件变成两个。「和坏代码保持一致」是唯一一种不该被一致性原则豁免的例外。

书里那句话的措辞比"不要变坏"更狠：

第 16 章 · 投资心态

即使你这次的具体改动并不需要重构，你也应当留意那些顺手就能修掉的设计缺陷。每当你修改任何代码，都试着在这个过程中让系统设计至少好一点点。如果你没有让设计变好，那你多半正在让它变坏。

「顺手就能修掉」的清单在 C/C++ 里非常具体，几乎每次改动都能挑到一条：

顺手能做的为什么它值得在那次改动里做
把一个 bool 参数换成 enum class 调用点从 f(x, true) 变成 f(x, Mode::Sync)；改动只有声明和几个调用点，但从此不用回查签名
给返回值加 [[nodiscard]] 你这次改动之所以要读这个函数，很可能就是因为有人忽略了它的返回值
把裸 malloc/free 对换成一个 std::unique_ptr 你已经在读这段代码了，边际成本最低；下一次改动就不用再验证一遍释放路径
把一处从阅读看不出原因的写法补上注释 你刚刚花时间搞懂了它，此刻你是唯一知道答案的人
删掉一个已经没人调用的函数 删代码是唯一零风险的设计改进

反面同样具体：新加的代码复制了旧代码里的坏模式，哪怕只是一次。旧代码里有个 `int` 返回错误码、`-1` 表示失败、但 `-1` 也可能是一个合法的计数——你新写的函数为了"保持一致"也这么干。于是错误处理这件事有了两个都不算数的真相。

16.4增量式改进，而不是等一场大重构

到这里一定有个现实的反驳：「照你这么说，我每次改动都要顺便重构，那功能什么时候交付？」书里正面回答了它，而且答案不是"永远选正确的方式"：

第 16 章 · 与现实的冲突

如果按「正确的方式」重构系统需要三个月，而一个又快又脏的修复只要两小时，那你可能不得不选择又快又脏的方式，尤其是在截止日期很紧的时候。或者，如果重构会造成不兼容、影响到许多其他人和团队，那么重构可能就不现实。

尽管如此，你还是应当尽可能抵制这些妥协。问自己一句：「在我当前的约束之下，这是我能做到的、创造干净设计的最好版本吗？」也许存在另一种做法，几乎和三个月的重构一样干净，但几天就能做完？

「两小时 / 三天 / 三个月」这三档是关键。它把"要不要重构"这个容易吵架的是非题，变成了一个可以当场比较成本的选项题。评审时这句话比"我觉得这样不好"有力得多：

「三个月的大重构我不主张。但这里有个三天的版本：把 ttl 和 sync 收进 PutOptions，后面加任何选项都不用再动调用点。要不要在这次改动里做掉？」

还有一个更常被忽略的中间档：把大重构拆成能独立落地的几步，这次只做第一步。比如你发现"过期时间"这个概念同时活在 put、磁盘格式、以及 GC 线程里——这就是一个横跨三处的知识。三天做不完，但你可以这次先把 PutOptions 立起来（只是接口层的一步），下次改 GC 时再把内部表示收进去。每一步单独看都是"战略的"，合起来就是那个大重构。

另外别忘了书里那句组织层面的建议：每个开发团队都该规划出一小部分固定工时用于清理和重构。把它写进排期，而不是指望"等这波需求忙完"——那波需求永远不会完。

16.5注释先行：改代码之前先改契约

第 15 章讲过"注释优先"这个开发流程：先写接口注释，再写实现。在修改既有代码时，这条流程的价值会翻倍，因为它顺手解决了本章最实际的一个问题——注释会随着代码改动而失效，而失效的注释比没有注释更糟：它让人不再相信所有注释。

把"先改注释"当成改动的第一步，有三个具体收益：

  1. 你会先看到全部约束。接口注释是这个模块唯一一处"所有调用方依赖什么"的完整陈述。把它读一遍再动手，比直接搜索调用点更可靠——搜索会漏掉那些通过函数指针或模板间接调用的地方。
  2. 你会更早发现改动的真实规模。如果改完注释你发现要加三行"注意：当 X 时，返回值的含义会变成 Y"，那说明这次改动的真实成本不是三行代码，而是接口开始变浅。这时候停下来还来得及。
  3. 注释会保持准确，因为它在你的视野里。书里关于位置的判断很实际：接口注释应该放在代码文件里、紧靠方法体，而不是放在 .h 里。
第 16 章 · 让注释留在代码附近

对于 C 和 C++ 这类把代码与头文件分开的语言，一种做法是把接口注释放在 .h 文件里方法声明的旁边。但它离代码太远了：开发者修改方法体时看不到这些注释，需要另外打开一个文件去找、去更新，这需要额外的工作。

有人会说接口注释就该在头文件里，这样使用者不必看代码就能学会用一个抽象。但使用者本来就不该读代码或头文件——他们应该从 Doxygen 之类工具生成出来的文档里获取信息，很多 IDE 也会在输入方法名时把文档显示出来。既然如此，文档就应该放在对开发者写代码最方便的位置。

这条建议会和你团队的既有习惯冲突（很多 C++ 项目把注释全放头文件）。这里的取舍很清楚：注释的第一使用者是改代码的人，不是读文档的人。如果你的工具链能从 .cpp 里抽取注释生成文档（Doxygen 完全可以），那就没有理由让它待在头文件里慢慢腐烂。

剩下的几条维护规则，都是同一句话的推论——让注释待在它必然会被人看见的地方，并且只写一份：

  • 别把解释写进提交信息。一段"这里为什么必须加这个 fence"的推理，如果只活在 commit message 里，下一个人重构掉它时不会去翻 git log。信息放在代码里，提交信息里可以再留一份副本。
  • 别重复。同一个设计决策写两处，改的时候必然只改一处。宁可在一处写全，在另一处只留一句「见 xxx 处的注释」——引用失效时读者立刻会发现（找不到目标），而重复失效时读者根本不会发现。
  • 不要在 A 模块里解释 B 模块的行为。调用点上方那句「这里会顺带把 buffer 落盘」，一旦 B 的实现改了就是假信息。
  • 提交前扫一遍自己的 diff。三分钟，能抓到"注释没跟上"和"忘了删调试代码"。

最后一条来自书里的一个洞察，它决定了注释能否长期存活：越抽象的注释越容易维护。「本函数把请求路由到负责该 key 的分片」不会因为分片算法从取模换成一致性哈希而失效；「用 key 的 CRC32 对 8 取模」明天就会过期。写注释时优先写前者，把后者留给代码。

练习这是战略改动还是战术补丁

五个真实风格的改动描述。判断它属于哪一种。注意：判断依据不是改动大小，而是它把新知识放在了哪里。

给 RingBuffer::push 加一个 bool overwrite 参数：满了就覆盖最老的一条。已有的 14 个调用点全部传 false。

14 个调用点被牵动，全部传同一个值——这本身就是信号：那 14 处根本不关心这个参数。真正的信息是"有两种缓冲语义"，那就该是两个类型（RingBuffer / OverwritingRingBuffer）或一个构造时的策略，而不是每个调用点都要回答一次的问题。

发现 parse_header() 和 parse_body() 各自实现了一遍 CRLF 跳过逻辑。把这段抽成 skip_crlf() 放进同一个文件，两边都调它。

这是第 5 章的后门泄漏被修掉：两个函数都懂"行结束符是什么"这条知识。抽成一处之后，改协议解析只动一个地方。它甚至没改变任何公开接口——最便宜的那种设计改进。

一个函数返回 std::pair<std::string, bool>，新需求要再加一个 size_t。于是改成 std::tuple<std::string, bool, size_t>。

调用点从 .first/.second 变成 std::get<2>——每个读者都必须回查声明才知道 get<2> 是什么。这正是第 18 章要讲的"通用容器使代码不明显"。改法：定义一个带名字字段的 struct ParseResult，三个字段各自可读。

修一个越界 bug 时，顺手给这个模块的 size_t len 参数加了一条前置条件断言，并在注释里写清 len 不含结尾 NUL。

你已经在读这段代码、已经搞懂了它的约定——此刻补注释的边际成本接近零，收益是下一个人的认知负荷直接下降。这就是 16.3 那张表的核心：顺手改掉的东西，成本被这次改动摊掉了。

为了绕开一个加锁顺序问题，在调用处包了一层 std::lock_guard，并把原来的 mutex 改成 recursive_mutex，让重入不再死锁。

把锁改成可重入，等于宣布"这个模块的加锁顺序不需要被理解"——它消掉了唯一的诊断信号，而不是消掉问题。这是"最小改动"最典型的恶性形态：它让系统看起来正常，同时把一条本该显式的约束藏进了无意识里。正确动作是找出那条顺序，把它写进接口注释，并用一个断言或分层锁去强制它。

练习把补丁改写成方案

有人在评审里提了这样一个改动：Connection::send() 现在遇到 EAGAIN 会直接返回错误。新需求要求"发送失败时自动重试两次"。作者的最小改动是在 send() 里加一个 for (int i = 0; i < 3; i++) 包住 ::send() 调用。

用 16.2 的三个问题过一遍：这次改动让哪个模块多知道了什么？改完之后，这条知识活在接口里还是记忆里？有没有一个只贵一点点的版本？

① 多知道的一件事：重试策略。而且它被放在了最底层。send() 从此隐含一条义务：它在返回之前会占用调用线程并可能重试。这条信息不在签名里，也不在返回值里。

② 它活在记忆里，而且有三个具体的坏后果：

  • 上层无法感知延迟。一次 send() 现在可能阻塞三次 EAGAIN 的时间；调用方如果本来就在一个必须快速返回的事件循环里，它被无声地改变了行为。
  • 与 sync/超时机制打架。如果外层已经有一套超时，两层重试会叠乘，实际最坏延迟变成 3×N。
  • 重试粒度错了。::send() 在部分写入后返回 EAGAIN，直接重试会把已发送的字节再发一遍——除非用 send() 的返回值推进偏移量，而这正是作者没写的那部分。

③ 只贵一点点的版本：把重试变成调用方可见的一个参数，或干脆不做。

// conn.h
struct SendResult {
  size_t bytes_sent;   // 本次实际写入的字节数
  int    err;          // 0 / EAGAIN / 其他 errno
};

// 只做一次写入尝试。返回 EAGAIN 表示内核缓冲已满，
// 调用方应等待可写事件后从 bytes_sent 处继续。
SendResult send_once(std::span<const std::byte> buf);

然后把"重试两次"放进调用方那层的一个小函数里，并给它一个超时预算。这样：接口里没藏行为，上层能算延迟，部分写入也被正确推进。改动量比"加个 for 循环"多十来行，但它把这条知识从三个人的记忆里挪进了两个函数的契约里。

如果这个 send() 的调用点有二十个、而只有这一个需要重试——那就更该这么做。如果二十个都需要，那说明"重试"是这个模块的默认语义，应该改在模块内部并在接口注释里写明最坏阻塞时间。两种都可以是战略的；唯一不能接受的是"改了行为但没人告诉你"。

练习一句话评审

能直接贴进 MR 的话：「这个改动让 put() 多知道了『过期时间』和『是否落盘』两件事，但它们现在只能靠调用点传第三个、第四个位置参数来表达——每个调用点都得回查签名，加第五个选项时还要再改一遍所有签名。建议收进一个 PutOptions（带默认值的结构体），这次改动的实际代码量不会增加，但后续加选项不用再动任何调用点。另外顺手把 put() 的接口注释补一下：ttl_ms=0 的语义、以及并发写同一 key 的可见性顺序，这两条目前只存在于实现里。」

这句话的结构可以复用到任何"加参数"的评审上：指出它让哪个模块多知道了什么 → 指出这份知识目前存在哪（位置参数 / 调用点 / 记忆）→ 给出一个成本相近的替代 → 顺手要求补齐契约。前三步让作者服气，第四步让这次改动在结束时不欠债。
