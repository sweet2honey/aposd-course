术语表

只收录你会在书里、评审里真正遇到的词。定义按中文译本用词，括注英文原词——搜英文原书和论文时要用后者。按章序分组，每章只在该组出现一次。

怎么用：评审时想不起某个词怎么说，先来这里找。每条都带一句「避免这样说」，因为说错词的代价比不说更大——说「耦合度高」没人能改，说「信息泄漏」对方知道要找什么。

第 1–5 章 · 概念地基

复杂性、症状、成因、深模块、信息隐藏

复杂性complexity

任何使系统难以理解和修改的东西。与系统规模、功能多少都无关；它是开发者在特定时刻的体验，不是代码的固有属性。

避免这样说：「代码量大」「功能复杂」——这两者都不是本书的复杂性。

→ L2 · 第 2 章

变更放大change amplification

复杂性症状之一：一个概念上很简单的改动，却要在很多地方重复修改。典型判据是「改一个字段名，编译器报了一串文件的错」。

避免这样说：「耦合度高」——太泛，说不出是哪种痛。

→ L2

认知负荷cognitive load

复杂性症状之一：完成一个任务需要预先掌握多少知识。一行代码也可能带来极高负荷——比如 allocate 之后必须由调用者 free。

避免这样说：用「代码难读」代替它。难读是表现形式，认知负荷是量化口径。

→ L2

未知的未知unknown unknowns

复杂性最糟的症状：你不仅不知道该怎么改，甚至不知道这里有问题。编译错误、崩溃都属于「已知」；安静的错答案才是这一类的典型。

避免这样说：「不熟悉代码」——那是人的问题，这是系统的问题。

→ L2、L4（写清非正式接口可消除它）

依赖dependency

复杂性的成因之一：某段代码不能被孤立地理解和修改，改它必须先看别处。它导致变更放大与认知负荷。

→ L2

晦涩obscurity

复杂性的成因之一：重要的信息不明显——名字太泛、单位未注明、关键约束只存在于某人脑子里、同一件事有两种写法。它导致未知的未知与认知负荷。

避免这样说：「可读性差」。晦涩特指缺失重要信息，不是排版不好看。

→ L2

战术编程tactical programming

只以「让功能跑起来」为目标的编程方式。每个决定单独看都情有可原，累积起来却让系统越改越难。其极端形态叫战术龙卷风：产出惊人、身后一地废墟，账单由接手的人付。

→ L3

战略编程strategic programming

同时以「好设计」和「能工作」为目标。要求几乎每个任务都如此，而不是等到大重构才想起来。核心动作是把总开发时间的 10–20% 投在设计上（主动投资 + 被动投资）。

→ L3

模块module

本书中的广义词：类、子系统、服务，甚至一个函数或方法。每个模块由接口（使用者必须知道的一切，即「做什么」）与实现（怎么做）构成。

→ L4

深度depth

模块的接口复杂度（成本）与它提供的功能（收益）之比。深 = 简单接口后藏着大量功能；浅 = 接口几乎是实现的镜像。

避免这样说：用「类的大小」当深度。大而浅完全可能，而且更贵。

→ L4

类炎classitis

「类应该小」推到极端后的病：系统被拆成大量极小的类，使用者要拼装许多东西才能完成一件小事。

→ L4

有效复杂度effective complexity

衡量深度时该用的口径：不是模块总共暴露多少能力，而是完成最常见那件事需要知道多少。Unix 默认顺序访问、随机访问才用 lseek，就是在压低有效复杂度。

→ L4

信息隐藏information hiding

造深模块最重要的技术（Parnas, 1972）：每个模块封装一个设计决策，把它嵌进实现、不让它出现在接口里。双重收益：简化接口（降认知负荷）+ 便于演化（被藏的知识在模块外无依赖）。

避免这样说：等同于 private。给每个字段配 getter/setter 是把私有变成公开，不是隐藏。

→ L5

信息泄漏information leakage

同一个设计决策反映在多个模块里，于是模块之间产生依赖。出现在签名里叫接口泄漏（明显）；两个模块都懂同一件事但签名干净，叫后门泄漏（危险）。

→ L5

时间分解temporal decomposition

按操作发生的时间顺序切分模块（读 → 改 → 写 = 三个类），导致读写双方都必须理解同一份格式知识，形成后门泄漏。

避免这样说：把「按流程拆」当成中性说法——在本书里它是一个明确的诊断结论。

→ L5

危险信号red flag

书中的使用约定：出现红旗就停下来，找替代设计。试过的替代方案越多，学到越多。信息泄漏是最重要的一面红旗。全书共 14 面，汇总见全书速查。

→ L1、L5、L21

第 6–10 章 · 通用性与例外

让模块更深，以及把错误变少

有点通用somewhat general-purpose

指模块的功能反映当前需求，但接口不反映当前需求——接口要通用到能支撑多种用途，同时让今天的需求用起来不难。「有点」是关键限定：通用到过头（比如把文本操作降到单字符粒度）会让调用方充满循环，还会牺牲性能。

避免这样说：「这个接口设计得很灵活」——灵活常指参数多、开关多；「有点通用」说的是接口形状，不是可调项数量。

['L6']

透传方法pass-through method

除了调用另一个方法之外几乎不做任何事的方法，被调用者的签名与它相似甚至相同。它让类变浅：增加接口复杂度却不增加系统功能，还在两层之间制造签名耦合。签名相同本身不是罪——调度器、多实现同一接口、真正增强行为的装饰器都合法；判据是「这个方法是否贡献了重要功能」。

避免这样说：「这只是一个包装」——装饰器也是包装，但它增加了功能；透传的关键特征是**没有**增加功能。

['L7']

传递变量pass-through variable

沿着一条长调用链向下传的变量，只有最底层的方法用得上，中间每一层都被迫知道它的存在。它导致变更放大：新增一个全局信息就要改整条链上的所有签名。常见解法是上下文对象。

避免这样说：「全局参数」——传递变量恰恰不是全局的，它是被人工往下递的。

['L7']

上下文对象context object

把系统的所有全局状态（配置、共享子系统、性能计数器）集中到一个对象里，每个系统实例一个；需要它的对象在构造函数里接收引用，并保存为成员。这样新增字段时，除上下文自身的定义外现有代码不用改。它带有全局变量的大部分缺点：字段用途不明显、无纪律会变成大杂烩、有线程安全风险——缓解办法是让字段尽量不可变。

避免这样说：「依赖注入容器」——上下文是显式传入的普通对象，不是自动解析的容器。

['L7']

净收益net gain

往系统里加的每一个设计元素（接口、参数、函数、类、定义）都会增加复杂性，因为开发者必须了解它；要带来净收益，它必须消除掉一些本来会存在的复杂性。这是判断「这一层/这个抽象该不该存在」的加减法口径。

避免这样说：「这样更规范」——规范不是收益；收益必须是「调用方需要知道的事变少了」。

['L7']

降低复杂性pull complexity downward

面对一个不可避免的复杂度时的取舍原则：如果它与模块提供的功能有关，就让模块自己在内部消化，而不是推给调用方。因为模块的使用者通常多于开发者。核心表述是「模块拥有简单的接口，比拥有简单的实现更重要」。

避免这样说：「封装得好」——降低复杂度特指**把复杂度从 N 个调用点搬到 1 个实现里**，不是把代码藏进 private。

['L8']

配置参数configuration parameter

类把本可自行决定的行为（缓存大小、重试次数、批量大小）导出成参数，让使用者去填。它常常是把难题转嫁给不懂的人的借口；配置值还会过时。应尽可能避免，或在导出时提供合理的自动默认值。判据是「用户能比我们确定得更好吗」。

避免这样说：「可配置性是优点」——只在用户确实更懂（如业务优先级）时才成立。

['L8']

异常屏蔽exception masking

在系统低层检测并处理异常情况，使高层完全不知道它发生过（TCP 重传丢包、NFS 挂起等待服务器恢复）。它让类变深：接口里需要关心的异常更少，同时以「掩盖异常的代码」增加了功能。只在模块外部不需要该信息时成立；把所有网络错误都吞掉会让上层写不出健壮应用。

避免这样说：「吞掉异常」——屏蔽是**正确处理**后的不上报，吞掉是不处理还不上报。

['L10']

异常聚合exception aggregation

不在每个可能出错的地方各写一个 handler，而是让异常传播到一个能覆盖最多情况的地方统一处理；错误消息在抛出时生成、随异常带上来。与异常屏蔽相反：聚合适合异常会穿过多个栈层的情况，屏蔽适合低层就能处理的情况。

避免这样说：「统一错误处理」——聚合的关键是「一个 handler 覆盖多个来源」，不是「所有错误都长一个样」。

['L10']

通过定义规避错误define errors out of existence

重新定义操作的语义，使原本的「异常情况」成为正常行为的一种，从而根本不需要报错。例：Tcl 的 `unset` 从「删除变量」改成「确保变量不再存在」；Unix 的删除允许文件仍被打开；子串/切片把越界当作取交集。这是减少「必须处理错误的地方」最有效的一招。

避免这样说：「容错」——容错是出错后能恢复；这里是把「错」的定义改掉，让它不发生。

['L10']

特殊情况special case

任何使控制流偏离正常路径的条件（不只是语言层面的异常）。它会让代码里混入 `if`，难以理解且容易出错。最好的消除方式是把正常情况设计成能自动覆盖特殊情况——例如用「空选区」代替「没有选区」的布尔标志。

避免这样说：「边界情况」——边界是输入范围的端点；特殊情况指的是**需要单独分支**的那一类条件。

['L10']

第 11–15 章 · 设计与表达

设计两次、注释、命名

设计两次design it twice

同一个设计问题（接口、类、实现机制）先算两遍，再比较优劣。不是「优化第一版」，而是强制产出两个互相不能推导的方案，用来暴露第一版里没被意识到的假设。成本只有几小时，而实现要几天。

避免这样说：「设计评审」——评审是评价一个方案；设计两次是**制造第二个方案**，没有第二个就没有比较。

['L11']

注释重复代码comments repeat the code

注释的详细程度与它所描述的代码完全一致，读者从注释得不到任何代码里没有的信息。典型形态是一行代码配一条注释，或者在注释里把被注释实体的名字拆成句子重拼一遍。它的成因多半是注释写得太晚：只剩代码可看，于是注释变成了代码的译文。

避免这样说：「注释太啰嗦」——啰嗦但有信息的注释仍然有用；重复代码的关键是信息量为零。

['L13']

接口注释interface comment

在模块声明之前，描述这个模块提供什么抽象：参数、返回值、副作用、错误、前置条件、调用义务。它定义了调用方眼中的模块，与实现注释严格分开。**如果接口注释不得不描述实现，说明这个模块是浅的**——这是判断深度最直接的证据之一。

避免这样说：「函数说明」——接口注释不是功能摘要，它是契约清单，尤其要写代码无法表达的部分（单位、边界、所有权、并发保证）。

['L13']

实现注释implementation comment

写在方法体内部的注释，说明这段代码在做什么、为什么这么做。大多数方法并不需要它——代码加接口注释已经够。只在三种场合值得写：长方法里的阶段划分、长或复杂的循环、以及从阅读看不出原因的写法（可以直接引用 bug 号）。

避免这样说：「过程注释」——实现注释的价值不在记录步骤，而在解释意图和理由；记录步骤会退化为注释重复代码。

['L13']

注释重复实体的名字using the entity's name in its comment

在注释里沿用它注释的那个变量/函数自己的词，导致注释只是名字的展开。写注释要换一套词，用它来说明这个实体**代表什么**：单位是什么、往哪一侧留白、失败时返回什么。

避免这样说：「注释写清楚点」——问题不是清楚程度，而是选词：同一套词不可能产生新信息。

['L13']

跨模块注释cross-module comment

记录一个必然横跨多个模块的设计决策（协议格式、状态机约定、必须同时修改的若干处）。难点不在写而在**放**：要放在开发者会自然撞见的位置。首选「必经之地」——例如状态枚举里列出新增状态值必须同改的所有文件；没有必经之地时，退而集中到一个 designNotes 文件，并在相关代码处留一句指向它的引用。

避免这样说：「架构文档」——跨模块注释的可发现性是第一位；一份没人打开的 wiki 页面不构成跨模块注释。

['L13']

designNotesdesign notes

书里用来放跨模块设计决策的中央文件，按主题分节（例如「Zombies」）。相关代码处只留一句 `// 见 designNotes 的 "Zombies"`，避免同一份文档被复制到多处。代价是它离代码较远，系统演化时容易失同步。

避免这样说：「设计文档」——designNotes 只装那些无处安放的决策，不是通篇设计说明。

['L13']

精度precision

好名字的两个属性之一：名字要足够具体，让读者在没看到声明的情况下也能猜对它指什么。太泛的名字（`getCount`、`x`、`block`）会把含义的负担推给注释和文档；而 `block` 同时表示文件块号和磁盘块号的那次事故说明，一个只是「合理接近」的名字也能造成长时间的数据损坏。

避免这样说：「名字取得更详细一点」——精度不是加长，是用几个词抓住最重要的方面（名字超过两三个词就变笨拙）。

['L14']

一致性consistency

好名字的另一个属性，含三条要求：① 同一用途始终用同一名字；② 同一个名字只用于那个用途；③ 用途本身要足够窄，让所有用这个名字的变量行为一致。第三条最常被忽略，也最难补救——它要求改名称的语义范围（如把 `block` 拆成 `fileBlock` / `diskBlock`），而不是改用法。

避免这样说：「统一命名风格」——一致性指的是**语义**的一致，不是前缀、驼峰这些排版层面的一致。

['L14']

谓词式命名predicate

布尔变量的名字应当是一个谓词，使读者从名字本身就能推出真假值各表示什么。`blinkStatus` 不合格（`status` 不传递极性，`blink` 描述行为而非状态），`cursorVisible` 合格。

避免这样说：「布尔量加 is 前缀就行」——`isXxx` 只是形式，关键是名字必须能被读成一个成立的命题。

['L14']

声明与使用的距离distance between declaration and use

作者引用并赞同的一条命名规则：名字的声明与它的使用之间的距离越大，名字就应该越长。距离近且整个用法一眼可见时，`i`、`j` 这样的短名完全够用；跨函数、跨文件、作为结构体字段被别处使用时，必须用精确的长名。它也解释了为什么「可读性必须由读者而不是作者来决定」。

避免这样说：「短名就是不好」——短名在近距离场景下更清楚，问题只出在距离大的地方。

['L14']

金丝雀canary in the coal mine

作者对注释作用的比喻：注释是复杂煤矿里的金丝雀。如果一个方法或变量需要很长的注释才能说清，那就是抽象没做好的危险信号。判断接口复杂度最好的材料就是它的接口注释——短而完整说明接口简单，必须罗列大量细节说明接口复杂，必须描述实现说明方法浅。

避免这样说：「注释写长了不好」——长短本身不是问题；只有注释**既完整又清晰**时它才是复杂度的有效指标，含糊的短注释不能当免死金牌。

['L15']

注释优先comments-first

先写注释再写实现的开发流程：类接口注释 → 最重要的公共方法接口注释与签名（方法体留空）→ 迭代到结构对了 → 最重要的成员变量声明与注释 → 填方法体并补实现注释 → 过程中新增的方法与变量同样先注释后代码。好处有三：注释质量更好；**设计更好**（在写代码前就能检查和调整抽象）；写注释更有趣。代码完成时注释也完成，不留积压。

避免这样说：「文档驱动开发」——注释优先是同一个人的设计动作，不是先写规格再由别人实现。

['L15']

第 16–18 章 · 在既有代码上工作

改动、一致性、显而易见

增量式改进incremental improvement

在既有代码上做改动的推荐形态：每次改动都在当前设计之上**再加一层好设计**，而不是「先按最小改动塞进去，将来再重构」。它要求的不是一次性大改，恰恰相反——它要求每次只改一点，但每次改完代码都比改前好一点。关键区别在于**方向**：战术补丁让系统退一步，增量式改进让系统进一步，两者可能只差几十行。与之配套的是「渐进式重构」：把一次大重构拆成若干次各自可运行、可评审的独立改动，而不是攒一个三周的巨型分支。

避免这样说：「小步快跑」——小步不等于改进；一个又一个小战术补丁也是小步，但方向朝下。

['L16']

注释属于代码不属于提交日志comments belong in the code, not the commit log

把设计知识写在代码里而不是提交信息里的原则。提交信息只被看到一次（或在 `git log` 里被极少数人翻到），而代码注释就长在使用它的地方，每次改动都会经过。判断标准：**如果这条信息能帮下一个读这段代码的人，它就必须在代码里**；提交日志适合放「为什么这次要改」，不适合放「这段代码为什么这样写」。注释跟着代码一起被 diff、被评审、被维护，因而不会腐烂。

避免这样说：「提交信息写详细点就够了」——没有 diff 上下文的提交信息，半年后没人能把它和具体某一行对应起来。

['L16']

在罗马时when in Rome

在既有代码库里工作时，先环顾四周找出既有约定（命名风格、成员声明顺序、错误处理方式、目录结构），然后**遵循它**，即使你认为有更好的做法。这是第 17 章给出的最实用的操作规则：新代码的首要目标是与周围协调，而不是局部最优。推翻旧约定需要两个条件同时成立——有当初不存在的新信息，且愿意把全部旧用法一起迁移（半迁移比不迁移更糟）。

避免这样说：「保持代码风格一致」——风格只是最表层的一层；这条规则覆盖接口形状、设计模式、不变量等更深的层面。

['L17']

不变量invariant

某个数据结构或模块**永远成立**的性质，例如「缓冲区始终 8 字节对齐」「每行以换行符结尾」「offset 始终相对文件头」。不变量的价值在于让读者能在任意一行代码上原地推断，不必回溯控制流是从哪进来的。它是第 17 章列出的一致性层面里收益最高的一层：每多一条不变量，下游就少一类特殊情况、少一个判断分支。不变量必须**写下来**（类注释）并且**有人守**（assert 或类型约束），缺任一条它半年后就不成立了。

避免这样说：「这是隐含约定」——隐含的不变量不是不变量，是未爆的 bug。

['L17']

显而易见obvious

代码的一种可验证性质：读者**不加思索地快速读过，对行为的第一次猜测就是正确的**。它不等于「简单」，也不等于「我写的时候觉得清楚」——判定权在读者手上，所以「读你代码的人说不明显，那它就不明显」。显而易见的代码需要的注释更少。书里从信息角度给出三种达成手段，按优先级排列：① 用抽象消除特殊情况以减少所需信息量；② 利用读者已有的信息（约定与期望）；③ 用好名字与战略性注释把信息交给他。

避免这样说：「可读性」——可读性偏排版与措辞；显而易见说的是**读者能否得到正确猜测**，衡量标准是猜对率而非舒适度。

['L18']

通用容器generic container

指 `Pair`、`std::pair`、`std::tuple` 这类把多个值打包的通用类型。它们用 `first`/`second` 或 `getKey()`/`getValue()` 这样的通用名字访问元素，因而**不携带任何含义**：读者无法从 `r.second` 判断它是「是否成功」还是「是否授予」。书里由此提炼出一条通用规则——**软件的设计应该使它易于阅读，而不是易于编写**：通用容器对写的人方便，对之后每一个读的人都是负担。需要多返回值时，定义一个字段有意义的专用结构体。

避免这样说：「结构化绑定就解决了」——`auto [a, b] = ...` 只是让写法变短，`a`/`b` 的含义仍然取决于被调函数的定义，读者照样要跳过去查。

['L18']

事件驱动编程event-driven programming

应用通过注册回调来响应外部事件（网络包到达、fd 可读、鼠标按下）的编程方式。它让**控制流极难跟踪**：处理函数从不被直接调用，而是在运行时被事件模块通过函数指针间接调用；即使在事件模块里找到了调用点，也无法确定具体哪个函数会被执行——那取决于运行时注册了哪些处理器。它本身是有用的技术，正确的补偿方式是给每个处理函数写接口注释，明确说明**何时被调用、在哪个线程、什么状态下不会被调用**。

避免这样说：「回调地狱」——那是嵌套过深的问题；事件驱动的晦涩是**控制流不可见**，扁平的回调同样晦涩。

['L18']

违反读者期望violating reader expectations

代码做了与通行惯例相反的事，却没有任何提示。书里的例子是构造函数起了后台线程，于是 `main()` 返回后进程仍在运行——读者按「main 返回即退出」的惯例推断，得到错误结论。C/C++ 里的常见形态：构造函数起线程或做阻塞 I/O、析构函数 join（于是析构可能卡几百毫秒）、`operator=` 里做深拷贝（看似 O(1) 实为 O(n)）。符合惯例的代码最显而易见；不符合时，**必须在声明处记录下来**，因为这类信息无法从签名推断。

避免这样说：「反直觉的设计」——反直觉本身不构成问题，不告知才是问题。

['L18']

第 19–21 章 · 趋势与收口

继承、测试、性能、红旗总表

接口继承interface inheritance

父类只声明方法签名、不提供实现，由每个子类各自实现（C++ 纯虚基类、Rust trait）。它的收益是把「同一接口适配多种底层机制」变成可能：同一套 I/O 接口，既可以读磁盘文件，也可以走网络套接字。本书对深度的另一种算法就藏在这里——**一个接口的不同实现越多，这个接口就越深**，因为它必须只保留所有实现共有的本质、把差异全部挡在接口之外。

避免这样说：「抽象」——太泛，本书的抽象是有具体判据的（共用本质、隔离差异）。

['L19']

实现继承implementation inheritance

父类不仅给出签名，还提供默认实现，并且通常带有实例变量，子类可以直接复用或覆盖。它的真实收益是消除子类间的重复，从而减小变更放大；代价是父类与子类共享状态，形成继承层次内部的信息泄漏。最坏情况下，要修改层次中任何一个类，都必须先完整理解整个层次。

避免这样说：「继承」——本书严格区分两种继承，说「继承」等于没说清方向。

['L19']

组合优于继承composition over inheritance

用一个小型辅助类承载共享功能，让原来的类按值持有（或持有指针）它，而不是从父类继承。它共享的是**代码**，不是**状态**，因此拿到了实现继承的好处而不引入父子之间的状态依赖。作者给的第二顺位方案是：如果不得不用实现继承，就把父类管理的状态与子类管理的状态分开，子类只能只读访问。

避免这样说：「多用组合」——要说出被共享的是代码还是状态，否则这条建议没有可操作性。

['L19']

开发的增量单位unit of development

渐进式开发是对的，但每个增量应当是**抽象**而不是**功能**。功能可以推迟到真正需要时再做；一旦确认需要某个抽象，就应当一次设计到位（至少覆盖一组合理完整的核心功能），而不是零散地一块块拼出来。书中认为这是敏捷实践最容易被误读成战术编程的地方。

避免这样说：「小步快跑」——它只说节奏，没说要交付什么；本书关心的是每个增量留下的是功能还是抽象。

['L19']

测试驱动开发test-driven development

先写单元测试、再写实现，直到测试变绿。作者自称是单元测试的坚定拥护者，但不推荐 TDD 作为常规开发方式：它把注意力锁在「让这个测试通过」上，而任何时刻都很容易再写一个功能，于是没有一段时间是留给设计的，属于纯粹的战术编程。他点名一个例外：**修 bug 时**应先写一个因该 bug 而失败的测试，再修，这样才能确认测的真是那个 bug。

避免这样说：「测试先行」——作为一般主张本书不同意；它只在修 bug 这个场景被明确推荐。

['L19']

关键路径critical path

执行最常见任务时**最少**需要执行的那段代码。它不是「最热的函数」这种统计概念，而是一个设计目标：把正常情况抽成一条无分支的快车道，让所有特殊情况在入口一次判定后就被分流到路径之外。围绕关键路径重设计是本书处理性能问题的核心技术，前提是先用度量确认瓶颈确实在这里。

避免这样说：「热点代码」——热点是测出来的现状，关键路径是你想要达到的设计。

['L20']

理想代码ideal code

暂时忘掉现有类结构，只问「完成这个任务最少需要执行哪些代码」，据此写出的一段假想代码。它可能和现有结构冲突、可能不现实，但提供了「这段逻辑最简最快能到什么程度」的标尺。下一步是找一个尽量接近它、同时保持干净抽象的新设计。

避免这样说：「重写一遍」——理想代码不是交付物，是靶子。

['L20']

根本性修正radical fix

相对于「在现有结构上微调」的另一种做法：引入缓存、换算法（平衡树换列表）、更换通信机制等。它通常能一次性消掉大片开销，而且可以用本书的设计技术干净地实现。作者的建议是先找根本性修正，找不到才退回到「围绕关键路径重设计」这套不得已的手段。

避免这样说：「重构」——重构不改行为；根本性修正恰恰是要改性能特征。

['L20']

微基准microbenchmark

只测量单个操作成本的小程序，用来建立「什么贵、什么便宜」的直觉。RAMCloud 项目花几天做了一个微基准框架，之后添加一个新基准只要五到十分钟，于是攒下了几十个。低门槛是关键——门槛够低，度量才会变成习惯，而不是一次性运动。

避免这样说：「压测」——压测看的是系统整体吞吐，微基准看的是单个操作的成本，两者不能互相替代。

['L20']

千刀万剐death by a thousand cuts

完全忽视性能时的典型后果：大量轻微的低效分散在整个代码库里，每一处都不致命，但没有一处单独改进能带来明显效果。系统可能比应有的速度慢五到十倍，而且事后极难挽救。它与「逐条语句优化」是两个极端，本书主张走中间路线——用性能的基本知识选出天然高效的设计。

避免这样说：「性能不好」——这个词掩盖了关键区别：是有单点瓶颈，还是遍地小刀。两者的解法完全相反。

['L20']

缓存缺失cache miss

数据不在片上缓存、必须从 DRAM 取回，代价约数百条指令时间。在多数程序里，整体性能取决于缓存缺失与计算成本的比值，而不是算法复杂度。它也是本书「简单即性能」论断的物理基础：更连续的内存布局、更少的层间跳转、更少的间接访问，都会直接减少缺失。

避免这样说：「内存慢」——慢的不是内存带宽，而是缺失带来的停顿；顺序访问和随机访问差两个数量级。

['L20']

战略投资strategic investment

每次改动都留出约 10–20% 的时间用于改善设计，而不是等功能上线、危机过去之后再清理。它的前提假设是：复杂性会持续累积，而推迟的成本带利息。作者在结论里强调，一旦方法熟练，好设计实际上并不会比草率的设计花更多时间——因为省下的时间只是被推迟了。

避免这样说：「技术债」——债务暗示可以一次性还清；本书认为设计是永不结束的持续过程。
